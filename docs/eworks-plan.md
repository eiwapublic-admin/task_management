## 1. 目的と範囲

### 目的

1. FileMaker「eWork2」で行っている**出勤簿の作成（月締め・有休管理・出勤簿 PDF）を、現行機能のまま**新システムへ移す
2. **勤怠入力（QR 打刻）を新設**し、現場スタッフ本人のスマートフォンで出勤・退勤を記録する
3. 勤務体系から**毎月の勤務予定を自動で組み**、**予定と実績の相違をいつでも検知**できるようにする
4. 画面をモダンなデザインに刷新し、Mac／Windows／iPhone／iPad のどれでも同じ機能を使えるようにする

### 範囲に含むもの

| 区分 | 内容 |
|---|---|
| 勤怠入力（新規） | 現場ごとの出勤用・退勤用 QR コード、アプリ内の読み取り、打刻記録、位置情報の記録、圏外時の一時保存 |
| 勤務予定（現行＋強化） | 出退勤パターン、担当者ごとの曜日別勤務体系、月次予定の自動作成（毎月自動＋手動の再作成） |
| 予定と実績（新規） | 本人用カレンダー、管理者用のスタッフ切替・一覧、相違の検知と「要確認」一覧、通知 |
| 出勤簿（現行踏襲） | 勤務表月締め一覧、月締め（日別一覧）、日別入力窓、休憩・残業・休日時間の計算、交通費・皆勤・通勤手当、出勤簿 PDF（個別・一括） |
| 休暇（現行踏襲） | 有給休暇の付与・繰越・残日数、特別休暇、欠勤、有給休暇申請書 PDF |
| マスタ | 現場（現行の作業マスタ）、出退勤パターン、担当者の勤務設定、休憩時間帯、スタッフ |
| 利用者 | 既存タスク管理の利用者＋現場スタッフ。**招待制の利用者登録** |
| 基盤（既存を踏襲） | 帳票 PDF、メール、写真の添付・保管、バックアップ、ログ |

### 範囲に含めないもの

| 項目 | 理由 |
|---|---|
| 端末管理（端末登録申請一覧・モバイル設定ファイルの送信） | 依頼元の指定（現在未使用）。FileMaker Go 用の仕組みで、新システムでは招待制の利用者登録に置き換わる |
| 勤務管理システム（`eiwa.razor.jp` の出退勤システム）との連携（マスター取り込み・実績 CSV 取り込み） | QR 打刻に置き換わるため不要になる（17章③で確認） |
| 支給額の計算（時間給 × 時間。現行も「金額付」帳票は作成中のまま未使用で、時間単価の項目が存在しない） | 給与計算は対象外。時間数と手当の有無までを扱う |
| 売上系伝票の取り込み・受注／売上伝票番号との紐づけ、報告ログ（Bot）、FileMaker Go 用の iPhone 画面 | 現行でも旧機能・バックアップ扱い（17章⑭で確認） |

## 2. 結論（先に要点）

- **作り方**: 販売管理（eSales）と同じ形にする。内部（リポジトリ・データベース・基盤コード）は既存タスク管理アプリに統合し、**入口は別アプリ「eWorks」**（専用 URL・専用アイコン・ホーム画面に単独で追加できる PWA）
- **打刻**: 現場に貼った QR を**アプリ内のカメラで読む**。サーバーの時刻で記録し、打刻の生データは書き換えない。位置情報を添えて「現場以外での打刻」を判別する
- **予定**: 現行の「担当者の勤務設定（曜日別の出退勤タイプ）」をそのまま引き継ぎ、**毎月 20 日ごろに翌月分を自動作成**。現行と同じく手動の一括作成・個別の再作成もできる
- **相違の検知**: 未出勤・遅刻・早退・退勤漏れ・予定外の出勤・現場違いなどを 5 分おきに判定し、管理者のホームと「要確認」一覧に常時表示。**始業時刻を過ぎても出勤がない場合は管理者へ通知**（代わりの手配に間に合わせる）
- **出勤簿**: 現行の計算（休憩の自動控除、通常／残業／休日、有休の付与と繰越）を仕様として文書化し、**過去月を両システムで計算して一致を確かめてから**切り替える
- **費用**: **追加 0 円で運用できる見込み**（Cloudflare Workers・Supabase とも無料枠内）。課金が発生しうるのは 5-3 に挙げた 4 点だけで、いずれも既定では使わない
- **期間**: 17〜21 セッション。切替は **2027年5月（4月分の出勤簿から新システム）** を目安として提案（14章）

## 3. 現行システムの分析

### 3-1. 構成（3 つの仕組みで成り立っている）

| 仕組み | 役割 | 新システムでの扱い |
|---|---|---|
| **eWork2**（FileMaker） | 勤務表・月締め・休暇管理・出勤簿の印刷 | **移行対象** |
| **eSales_data**（FileMaker） | 担当者マスタ（氏名・所属・入社日・携帯電話）を eWork2 が参照 | スタッフ情報を eWorks 側に持つ（5-4） |
| **出退勤システム**（`eiwa.razor.jp`。カードのタッチで記録する Web システム） | 出退勤パターン・従業員の管理、タッチログ、CSV 出力。eWork2 が画面の表を読み取って取り込んでいる | **QR 打刻に置き換え**。切替後は不要（17章③） |

現行は「出退勤システムで実績を記録 → eWork2 の『実績 取り込み』で読み込み → 『予定実績 一覧』で確認・訂正 → 『eWork反映』で勤務表へ反映 → 月締め → 出勤簿印刷」の流れ。
最終タッチが数年前のままの従業員が多く、**実際には予定をそのまま実績として扱っている担当者が多い**と読み取れる（出勤簿の見出しも「実績 0 件なら『予定』、1 件以上で『実績』」）。

### 3-3. データの構造

```
担当者（eSales 担当者マスタ） ── 担当者作業マスタ（主要作業＝現場、曜日別の出退勤タイプ、例外の休憩時間、通勤手当）
        │                                   └─ 出退勤パターン（タイプ名・出勤予定時刻・退勤予定時刻）
        └─ 勤務表月締め（担当者 × 年月：月合計・皆勤・通勤・備考・有休の計算）
               └─ 勤務表日別（担当者 × 日：欠勤・交通費・備考・祝日）
                      ├─ 勤務表作業明細（件名＝現場、予定の開始／終了、実績の開始／終了、休憩調整、残業、休日）
                      │      └─ 写真
                      └─ 有休取得実績／特別休暇取得実績（担当者 × 取得日）
```

### 3-4. 勤務時間の計算（デザインレポートの計算式から）

| 項目 | 現行の計算 |
|---|---|
| 開始・終了時刻 | 手入力の実績 → 取り込んだ実績 → 予定 の順に、最初に値があるものを採用（**実績がなければ予定**） |
| 休憩（自動） | 設定された**休憩時間帯（最大 5 つ）**と勤務時間帯の重なりを差し引く。担当者作業マスタに**曜日別の例外休憩**があればそちらだけを使う |
| 総時間 | 終了 − 開始 − 休憩（自動）。時間は「時＋分÷60」を小数 2 桁に丸め |
| 作業時間 | 総時間 − 追加休憩（手入力） |
| 通常時間 | 作業時間 − 残業時間（手入力） − 休日時間（手入力） |
| 欠勤 | その日の作業時間を 0 にする |
| 月合計 | 通常・残業・休日・交通費の合計。件名（現場）別の小計を予定／実績の 2 列で表示 |
| 手当 | 皆勤・通勤はチェックで付ける。通勤手当の金額は担当者作業マスタから取得 |

残業と休日の時間は**自動判定ではなく手入力**である点は現行どおり引き継ぐ（自動判定の提案は 13章）。

### 3-5. 勤務予定の作成（スクリプト「p_担当者予定登録()」ほか）

- メニューの「予定一括作成」で、指定月の全担当者分を作成。担当者ごとの作成もできる
- 1 日ずつ、**曜日別の出退勤タイプ**から出勤予定・退勤予定の時刻を入れる。曜日別の指定がない担当者は、月〜金に既定のタイプを入れる
- **祝日は予定を入れない**（祝日は外部の祝日データから取得）
- 件名には担当者の主要作業（現場）の名称を入れる
- 出退勤パターンが不明・曜日別タイプが未設定の担当者は飛ばし、人数を結果に表示

### 3-6. 有給休暇・特別休暇（勤務表月締めの計算式から）

| 項目 | 現行の計算 |
|---|---|
| 付与日数 | 入社からの継続月数で決定: 6か月=10日、18か月=11日、30か月=12日、42か月=14日、54か月=16日、66か月=18日、78か月以上=20日 |
| 付与期間 | 入社月の 6 か月後の月の **1 日**から 1 年間 |
| 繰越 | 前期間の残日数を繰り越す。**繰越分から先に消化**し、使い切れなかった繰越分は期間末に消滅 |
| 残日数 | 繰越 ＋ 今期付与 − 今期取得（出勤簿には「有休付与日数（内 繰越）／今期間取得済日数／残日数（内 当月）」を表示） |
| 特別休暇 | 有休の付与がある担当者に 1 期間 5 日。取得日数と当月分を表示 |
| 単位 | 1 日単位（有休の日に勤務時間があっても 1 日として数える。時間単位の取得はなし） |

> 注意: 付与日数は全員に**通常の労働者の表**を適用している。週の所定労働日数が少ないパートの方は、
> 法令上は日数の少ない「比例付与」の表が適用される。現行は法定以上を付与している形なので違反ではないが、
> **2026-11-14 に「現行どおり」と決定**（決定事項 2）。

### 3-8. 現行の課題

| 課題 | 新システムでの解消 |
|---|---|
| 実績の記録が別システムで、取り込み・反映の手作業が要る | QR 打刻がそのまま勤務表の実績になる |
| 予定と実績の違いは、月ごとの一覧を開いて目で探す | 相違を自動で検知し、常に「要確認」に出す |
| 現場スタッフ本人は自分の予定・実績を見られない | 本人用のカレンダー画面 |
| 勤務設定に履歴がない（変更すると過去月の再作成に影響） | 勤務体系に「適用開始日」を持たせる |
| 有休の申請・承認は紙 | 申請 → 承認をアプリ内で（申請書 PDF も残す） |
| 利用者の追加が管理者の手作業（アカウント作成・設定ファイル送付） | 招待リンク／招待 QR で本人が登録 |
| Mac／Windows の FileMaker が必要。iPhone 用は別画面 | ブラウザだけで全端末同じ機能 |

## 5. 全体方針

### 5-1. eSales と同じ「内部は統合・入口は別アプリ」にする

販売管理（eSales）で 2026-11-14 に決定済みの方式に合わせる。

| 層 | eWorks の作り |
|---|---|
| リポジトリ | 既存 `eiwapublic-admin/task_management` に追加。コードは `src/works/`・`worker/lib/works/` に閉じる |
| 入口 | **3 つ目の Worker `eworks`**（例: `eworks.eiwa-public.workers.dev`）。`worker/works.js`・`wrangler.works.jsonc`・Vite の入口 `works.html` |
| PWA | 専用の manifest（名前 `eWorks`、専用アイコン）と Service Worker。Mac の Dock・Windows・iPhone・iPad に単独のアプリとして追加できる |
| データベース | 既存の Supabase プロジェクト。テーブルは **`works_` 接頭辞**。画面からは直接つながず Worker（service role）経由のみ＝既存方針どおり |
| ログイン | 既存の `users` と JWT（`token_version` による即時失効つき）を共用。ID・パスワードは共通で、**アプリごとに 1 回ログイン** |
| 共通部品 | UI トークン・`src/styles/ui.css`・`Combobox.jsx` などは 3 アプリで共有 |

この形にする理由:

- **現場スタッフにタスク管理（メール由来の業務情報）を見せない**ことを、入口の分離で確実にできる。eWorks の Worker は `/api/works/*` しか持たない
- 帳票 PDF・メール・写真・Push 通知・ログ・バックアップの実装をそのまま使える
- Supabase の無料枠は 2 プロジェクトまで。タスク管理・eSales・eWorks を別プロジェクトにすると有料になる
- eSales の Phase 1 で行う「入口の実機確認（4 端末）」の結果と手順を、そのまま eWorks でも使える

**既存アプリ側に必要な変更（1 点だけ）**: 現場スタッフ用の役割（`field_staff`。11章）を `users` に追加するため、
**タスク管理と eSales のログインが `field_staff` を拒否する**ようにする。これを入れるまで現場スタッフの招待は行わない。

### 5-2. 既存の作りに合わせる

| 項目 | 方針 |
|---|---|
| フロント | React（Vite）。[`ui-standard.md`](./ui-standard.md) に準拠 |
| QR の読み取り | 既存の `src/lib/barcode.js`（`@zxing/library`。検針の機器番号読み取りで実績あり） |

| 帳票 PDF | 既存方式（HTML を画面外に全幅で描画 → `html2canvas` → `jsPDF`）。スキル `print-and-pdf-download` の注意点に従う |
| メール | 既存の Gmail 連携（下書き作成＋PDF 添付） |
| 写真 | 既存の `imageResize.js`（端末側で縮小）＋添付プレビュー（スキル `multi-env-attachment-preview`） |
| 通知 | 既存の Web Push（`worker/lib/push.js`） |
| 祝日 | 既存の `worker/lib/holidays.js`（現行 eWork2 と同じ「祝日名つきの公開データ」） |
| ログ | 既存 `activity_logs` に `works_*` 種別で記録 |

| 定期処理 | `eworks` Worker の Cron（5 分おき。相違の判定・通知、月次予定の自動作成） |

### 5-3. 無料枠の見通しと、課金が発生しうる点

| 資源 | 無料枠 | 現在（2026-11-14） | eWorks の追加（推定） | 判定 |
|---|---|---|---|---|
| Supabase DB | 500MB | 27MB（eSales 移行後は +150〜250MB の見込み） | 過去分 約 30〜50MB、以後 年 5〜8MB | **収まる**（3 つ合わせて 330MB 前後。年 1 回確認） |
| Supabase Storage | 1GB | 40MB | 現場写真 142 件＋新規分。数十 MB | 収まる。eSales が R2 を有効化した後は R2 に置く |
| Cloudflare Workers | 10 万リクエスト／日（アカウント合計）、Cron 5 本まで | 余裕あり | 打刻は 1 人 1 日数回。Cron 1 本追加（計 3 本） | 収まる |
| GitHub Actions | 月 2,000 分 | バックアップ・デプロイ | デプロイが 1 つ増える | 収まる見込み |

**課金の可能性があるのは次の 4 点**。いずれも既定では使わない。使う判断をする前に必ずお伝えする。

1. **Claude API**（13章の AI 機能を使う場合のみ。従量課金。既存の 1 日上限の仕組みの対象にする）
2. **Cloudflare R2**（無料枠 10GB。eSales で有効化を決定済み。eWorks 単独では不要）
3. **Supabase Pro（月 25 USD）**（DB が 500MB を超えそうな場合のみ。当面は不要）
4. **SMS での招待送信**（使わない。招待は QR・LINE・メールで渡す）

### 5-4. スタッフ情報の持ち方（eSales との関係）

現行は eSales の担当者マスタ（社員・得意先担当・仕入先担当が混在する 616 件）を参照している。
eWorks の稼働は eSales の切替（2028年1月）より先になる見込みのため、**eWorks 側に `works_staff`（スタッフ）を持つ**。

- 持つ項目: 担当者コード・氏名・ふりがな・所属・入社日・携帯電話・在籍状態。**給与関連の項目は持たない**（eSales の方針と同じ）
- **担当者コードは現行のまま**使う。eSales が稼働したら、担当者コードで eSales の担当者マスタ（`sales_contacts`）と紐づける
- 有給休暇申請書の連絡先は現行「eSales 担当者マスタの携帯電話を直接更新」だが、新システムでは `works_staff` の携帯電話を更新する

## 6. 勤怠入力（QR 打刻）の設計

### 6-1. QR コード

- **現場ごとに 2 枚**（出勤用・退勤用）。管理者が「現場マスタ」の「QR を印刷」から **A4 の掲示用 PDF** を出力する。
  出勤用と退勤用は**色と大きな文字で見分けられる**ようにする（例: 出勤＝緑の枠「出勤」、退勤＝橙の枠「退勤」、現場名を併記）
- QR の中身は URL（`https://<eWorks の URL>/p?c=<現場コード>&k=<in|out>&t=<合言葉>`）。合言葉は推測できない乱数で、DB にはハッシュだけを保存
- **再発行**すると古い QR は無効になる（掲示物の紛失・退職者による持ち出しへの対策）
- 同じ現場に複数の出入口があっても同じ QR を複数枚貼れる

### 6-2. 打刻の流れ（現場スタッフ）

```
ホーム（今日の予定）→［出勤を記録］→ カメラで QR を読む → 記録完了の画面（時刻・現場名・予定との差）
                    →［退勤を記録］→ カメラで QR を読む → 記録完了の画面（今日の勤務時間）
```

- ボタンは今の状態に合わせて 1 つだけ大きく出す（未出勤なら「出勤を記録」、勤務中なら「退勤を記録」）
- 記録完了は**大きなチェックと時刻、振動**で知らせる（早朝・屋外でも一目でわかるように）
- **時刻はサーバーの時刻**を使う（端末の時計をずらしても影響しない）
- iPhone の標準カメラで QR を読んだ場合はブラウザで eWorks が開き、ログイン済みならそのまま打刻。
  ただし iPhone では「ホーム画面のアプリ」と「Safari」でログインが別になるため、**アプリ内の読み取りを基本**とする

### 6-3. まちがい・不正への備え

| 場面 | 動き |
|---|---|
| 出勤していないのに退勤用を読んだ／出勤済みで出勤用をもう一度読んだ | 状況を表示して確認（「出勤の記録がありません。退勤だけ記録しますか」）。二重読み取りは 1 件にまとめる |
| 予定と違う現場の QR を読んだ | 記録はする。「現場違い」として要確認に出す |
| 予定のない日に打刻した | 記録はする。「予定外の出勤」として要確認に出す |
| QR を写真に撮って別の場所で読む | 打刻時に**位置情報**を記録し、現場の位置から離れていれば「位置不一致」として要確認に出す（打刻は止めない）。位置情報を許可しなかった場合は「位置情報なし」の印 |
| 電波が届かない（地下・機械室） | 端末に一時保存し、電波が戻ったら自動送信。「オフライン打刻」の印を付け、端末の時刻を参考値として記録 |
| 打刻を忘れた・まちがえた | 本人が**修正申請**（日付・時刻・理由）→ 管理者が承認。管理者が直接訂正することもできる |
| スマートフォンを持っていない・忘れた | 管理者が代理で入力（「代理入力」の印）。現場の共用タブレットで氏名を選んで打刻する方式は 17章⑤で要否を確認 |

### 6-4. 記録の持ち方

- **打刻の生データ（`works_punches`）は追記のみ**。訂正・取消は別の行として残し、元の記録は消さない
- 勤務表に載せる「採用時刻」は、打刻から 6-5 のルールで決め、管理者が訂正できる（訂正前の値と訂正者を残す）
- 勤務時間の客観的な記録として、**誰がいつどの方法で記録・訂正したか**を後から追える状態にする

### 6-5. 採用時刻の決め方（17章④で確認）

現行は、取り込んだ実績が予定とずれているとき、管理者が行ごとに「予定時刻で訂正」を押している。新システムの推奨:

| 打刻と予定の差 | 採用時刻 |
|---|---|
| 許容範囲内（既定: 出勤は予定の 30 分前〜5 分後、退勤は予定の 5 分前〜30 分後） | **予定の時刻**を自動で採用（管理者の手作業をなくす） |
| 許容範囲の外 | **打刻の時刻**を採用し、要確認に出す（遅刻・早退・超過。管理者が確認して確定） |

許容範囲は設定画面で変更できる。どちらの場合も打刻の生データは 1 分単位でそのまま残る。

## 7. 勤務体系と予定の自動作成

### 7-1. マスタ

| マスタ | 内容 | 現行との対応 |
|---|---|---|
| 現場 | コード・名称・詳細・位置（緯度経度・許容距離）・QR | 作業マスタ（21 件）＋位置と QR を追加 |
| 出退勤パターン | 名称・出勤時刻・退勤時刻・有効／無効 | 出退勤パターン（58 件）。出退勤システムからの取り込みをやめ、ここで直接編集 |
| 休憩時間帯 | 共通の休憩時間帯（最大 5 つ） | Parm の休憩時間開始／終了 |
| 勤務体系 | スタッフ × **適用開始日** × 曜日ごとの［パターン・現場・例外の休憩時間］、曜日指定がない場合の既定パターン、祝日の扱い、通勤手当 | 担当者作業マスタ（57 件）＋適用開始日を追加 |

- 画面は現行「担当者の勤務設定」と同じ**スタッフ × 曜日の表**。セルを押してパターンを選ぶ
- **適用開始日**を持たせるので、「来月から週 3 日に変更」を前もって登録でき、過去月の予定は変わらない
- 1 人が 1 日に 2 つの現場を回る場合は、同じ曜日に 2 行目を追加できる（現行の作業明細が 1 日複数行を許しているのと同じ）

### 7-2. 予定の作成

| 項目 | 内容 |
|---|---|
| 自動作成 | **毎月 20 日**に翌月分を全スタッフ分作成（日は設定で変更可）。結果は管理者へ通知（作成人数、設定不足で飛ばした人） |
| 手動作成 | 現行と同じ「予定一括作成」（月単位）と、スタッフ単位の再作成 |
| 祝日 | 現行どおり**予定を入れない**。祝日も勤務する現場・スタッフ向けに、勤務体系に「祝日も勤務」の指定を追加 |
| 会社の休日 | 年末年始・夏季などを「会社休日」として登録すると、その日は予定を入れない |
| 再作成時の保護 | **手で直した日・打刻のある日・休暇の日は上書きしない**（現行にはない保護） |
| 途中入社・退職 | 入社日以降・退職日までだけ作成 |

### 7-3. 予定の個別変更

- 管理者は日別入力窓で予定の時刻・現場を変更できる（代勤、時間変更、臨時の出勤）
- 変更があったら本人へ通知（13章）

## 8. 予定と実績の相違の検知

### 8-1. 検知する相違

| 種別 | 条件（既定値。設定で変更可） | 重要度 |
|---|---|---|
| **未出勤** | 予定の出勤時刻を 10 分過ぎても出勤の打刻がない | 高（管理者へ通知） |
| 遅刻 | 出勤の打刻が予定より 5 分を超えて遅い | 中 |
| 早退 | 退勤の打刻が予定より 5 分を超えて早い | 中 |
| **退勤漏れ** | 予定の退勤時刻を 60 分過ぎても退勤の打刻がない | 中（本人へ通知） |
| 超過 | 退勤の打刻が予定より 30 分を超えて遅い | 中（残業の入力漏れの確認） |
| 予定外の出勤 | 予定のない日・時間帯の打刻 | 中 |
| 現場違い | 予定と違う現場の QR | 中 |
| 位置不一致／位置情報なし | 現場から許容距離（既定 300m）を超える／位置情報が取れない | 低 |
| 休暇日の打刻 | 有休・特別休暇・欠勤の日に打刻がある | 中 |
| 訂正あり | 打刻と採用時刻が違う（修正申請・管理者訂正・代理入力） | 低（一覧で印を表示） |

### 8-2. 見せ方

- **管理者ホームの先頭に「要確認 n 件」**。サイドバーの「要確認」にも件数の印。どの画面にいても件数が見える
- 「要確認」一覧は日付・スタッフ・種別で絞り込み。行を押すと日別入力窓が開き、その場で確認・訂正
- 確認したら「確認済み」にする（誰がいつ確認したか、メモを残せる）。確認済みは一覧から消え、履歴で見られる
- **月締めの前に、未確認の相違が残っているスタッフを表示**（締め忘れ・確認漏れの防止）
- 本人のカレンダーにも同じ印を出す（本人が先に気づいて修正申請できる）

### 8-3. 判定のタイミング

- 打刻の時点（遅刻・早退・現場違い・位置・予定外）
- Cron の 5 分おきの巡回（未出勤・退勤漏れ）
- 判定は Worker 側の 1 つのモジュールで行い、画面ごとに判定を書かない

## 9. データモデル

### 9-1. 原則

- **現行の構造（月締め → 日別 → 作業明細）を保つ**。移行と突合を成り立たせるため、正規化し直さない
- 勤務のない日の空の行は作らない（現行は 1〜31 日を必ず持つが、新システムでは予定・実績・休暇のいずれかがある日だけ）
- 時間の計算は 1 か所（画面と Worker が同じモジュールを使い、保存時は Worker の計算値を正とする）
- 複数テーブルにまたがる書き込み（打刻 → 勤務区間への反映、月締め、予定の一括作成）は Postgres 関数で 1 トランザクション
- `anon`／`authenticated` には GRANT しない（service role のみ）

### 9-2. 主なテーブル

| テーブル | 内容 | 現行の対応 |
|---|---|---|

| `works_settings` | 休憩時間帯・許容範囲・予定作成日・会社休日 | Parm |
| `works_months` | 月締め（スタッフ × 年月：皆勤・通勤・備考・**状態（未締め／本人確認済み／締め済み）**・締め時点の合計） | 勤務表月締め |

## 10. 画面設計（UI／UX）

### 10-1. デザインシステム（eSales と揃える点・変える点）

| | 内容 |
|---|---|
| **揃える** | トークン（余白・角丸・文字サイズ・影）、共通部品（ボタン・入力欄・表・バッジ・モーダル）、画面の骨格（PC・iPad は左サイドバー、iPhone は下部タブ）、明るい画面に固定、状態の色（良＝緑・注意＝黄・不良＝赤） |
| **変える** | **アクセント色**、**アプリアイコン**、ホーム画面の構成（eSales は伝票、eWorks は今日の勤務とカレンダー） |

**どちらのアプリか一目でわかる工夫**:

- サイドバー上部とログイン画面に、アクセント色のアプリ名（`eWorks`）とアイコンを常に表示
- ブラウザのタブ・Dock・ホーム画面のアイコンを色と形で区別（eSales＝藍地に「e」。eWorks＝別の色地に時計をかたどった印）
- ヘッダの細い帯にアクセント色を使う（背景全体は塗らない＝視認性を落とさない）

**アクセント色の候補**（17章②で決定）。既存のタスク管理＝深緑、eSales＝藍 と区別できること、
相違の表示に使う赤・黄と紛れないことを条件にした。

| 案 | 色 | 印象 | 評価 |
|---|---|---|---|

### 10-2. 視認性と操作効率

| 方針 | 具体策 |

## 11. 利用者・権限・招待

### 11-1. 役割

| 利用者 | `users.role` | eWorks でできること |
|---|---|---|
| 現場スタッフ | **`field_staff`**（新設） | 自分の打刻・カレンダー・申請だけ。**タスク管理と eSales には入れない** |
| 既存の利用者（事務所） | `staff` | 自分の勤務＋（管理権限があれば）全員の勤務・月締め・マスタ・利用者 |
| 既存の利用者 | `owner` | 自分の勤務＋全員の閲覧（書き込み不可。既存アプリと同じ扱い） |
| 備品出庫限定 | `equipment_out_staff` | 自分の勤務だけ |

- 勤怠と休暇は個人情報のため、**全員分を見られるのは「eWorks 管理者」に指定した利用者だけ**にすることを推奨（17章⑥）。
  `users` に `works_admin`（真偽）を 1 列足し、依頼元が指定する
- 判定は必ず Worker 側で行う。現場スタッフの API は「自分のスタッフ ID」に固定し、他人の ID を指定しても読めない

### 11-2. 招待制の登録

```
管理者: 利用者 →［招待する］→ スタッフを選ぶ（または新規登録）→ 招待 QR／招待リンクが表示される
        → その場でスマートフォンに読ませる／LINE・メールで送る／紙に印刷して渡す
本人:   招待を開く → 氏名を確認 → ログイン ID とパスワードを決める → ホーム画面への追加の案内 → 利用開始
```

| 項目 | 内容 |
|---|---|
| 有効期限 | 発行から 7 日（設定で変更可）。**1 回使うと無効** |
| 招待の中身 | 推測できない乱数。DB にはハッシュだけを保存 |
| 紐づけ | 招待はスタッフ 1 人に対応。登録と同時に `users` と `works_staff` が紐づく（管理者の割り当て作業は不要） |
| 取り消し | 未使用の招待は一覧から取り消せる |
| パスワードを忘れた | 管理者が「再設定リンク」を発行（招待と同じ仕組み）。メールアドレスを持たない人でも使える |
| 退職・契約終了 | 利用者画面の「利用停止」で**即時にログイン不可**（既存の `token_version` による失効）。勤務の記録は残す |
| 機種変更 | 新しい端末で同じ ID・パスワードでログインするだけ（端末の登録は不要） |
| 総当たり対策 | 既存のログイン試行回数制限（KV）を共用。招待の入力にも同じ制限 |

顔認証・指紋認証でのログイン（パスキー）は 13章の提案。

## 15. データ移行

### 15-1. 方式

備品・廃棄物・eSales と同じ方式。FileMaker から CSV（または Excel）を書き出していただき、取込スクリプト（`scripts/import-works-*.py`）で検証 → 取込。
取込は何度でもやり直せる作りにし、並行運用の終わりに最終版をもう一度取り込む。

### 15-2. 対象と順序

| 順 | データ | 件数 | 備考 |
|---|---|---|---|
| 1 | スタッフ（eSales 担当者マスタのうち勤務管理対象） | 数十件 | 給与項目は書き出さない |
| 2 | 現場（作業マスタ）・出退勤パターン・担当者作業マスタ・休憩時間帯 | 21・58・57 件 | 使われていないパターン・退職者の設定は取込時に一覧で確認 |
| 3 | 有休・特別休暇の取得実績 | 1,062・404 件 | 残日数の計算に全期間が必要 |
| 4 | 勤務表（月締め・日別・作業明細） | 2,629・75,193・75,828 件 | 勤務のない空の日は取り込まない |
| 5 | 現場写真 | 142 件 | 17章⑪で要否を確認 |

**推奨: 全期間を移行する**（容量は小さく、出勤簿の保存義務と有休の繰越計算の両方を満たせる）。

### 15-3. 検証（突合）

- **勤務時間**: 直近 12 か月の全スタッフについて、通常・残業・休日の月合計と交通費計を新旧で比較。差があれば日単位で原因を特定
- **有休**: 全スタッフの付与日数・繰越・取得済・残日数を現行の出勤簿の表示と比較
- **帳票**: 数名分の出勤簿 PDF を新旧で並べて確認していただく
- 一致を確かめるまで、**出勤簿は FileMaker から出す**

| 個人情報 | 勤務実績・休暇・位置情報・携帯電話を扱う。全員分の閲覧は管理者に限定。現場スタッフの API は本人分に固定。位置情報は**打刻の瞬間だけ**取得し、常時の追跡はしない（招待時の案内に明記） |
| 通信・保存 | 既存と同じ（HTTPS、セキュリティヘッダ／CSP、パスワードは bcrypt、JWT は即時失効つき） |

| バックアップ | 既存の日次バックアップに含まれる。復元手順は [`disaster-recovery.md`](./disaster-recovery.md) |
| 保存期間 | 出勤簿などの労務関係の記録は法令上 5 年（当面 3 年）の保存が求められる。新システムでは削除せず保持する |
| 性能 | 打刻は 1 秒以内に完了画面を出す。月の表は 1 回の問い合わせで取得 |
| 障害時 | 打刻できない場合は端末に一時保存。長時間の障害時は管理者の代理入力で補う |

## 18. 依頼元の作業（Phase 0）

### 手順1: 確認事項への回答

17章の表の「推奨」と違うものだけお知らせください（「全て推奨のとおり」でも進められます）。

### 手順2: マスタと過去データの書き出し（FileMaker Pro）

eWork2 を FileMaker Pro で開き、次のレイアウトでそれぞれ**全レコードを表示**（メニュー「レコード」→「全レコードを表示」）してから、
メニュー「ファイル」→「レコードのエクスポート...」で **Excel（.xlsx）または CSV（UTF-8）** に書き出してください。
エクスポートするフィールドは「すべて移動」で構いません（計算項目も突合に使います）。

| レイアウト名 | 内容 |
|---|---|
| 作業マスタ | 現場 |
| 出退勤パターン_勤怠 | 出退勤パターン |
| 担当者作業マスタ | 担当者の勤務設定（曜日別タイプ・例外休憩は「繰り返し」を含めて書き出し） |
| Parm | 休憩時間帯などの設定値 |
| 勤務表月締め | 月締め |
| 勤務表日別 | 日別 |
| 勤務表作業明細 | 作業明細 |
| 有休休暇取得実績／特別休暇取得実績 | 休暇の取得実績 |

担当者マスタは eSales の「担当者マスタ」から、**勤務管理の対象者だけ**を対象レコードにし、
**担当者コード・氏名・ふりがな・所属・入社日・携帯電話**の 6 項目だけを書き出してください（給与関連は含めない）。

### 手順3: 現場の情報

QR を貼る現場ごとに、**名称・住所（または地図上の位置）・QR を貼る場所の候補**をお知らせください（作業マスタ 21 件が対象）。

### 手順4: 現場スタッフの端末の確認

現場スタッフの人数、スマートフォンの有無（iPhone／Android）をわかる範囲でお知らせください（17章⑤・⑦）。

### 手順5: 試行に協力していただく現場の選定

Phase 3 の試行（2027年2月の目安）に使う現場を 1〜2 か所と、協力していただくスタッフ数名を決めてください。

**課金が発生する作業はありません。** 新しい Worker（`eworks`）の作成は Cloudflare の無料枠内で、デプロイの前に一言確認します。

## 19. リスクと対策

| リスク | 対策 |
|---|---|
| 現場スタッフが操作に慣れない・打刻を忘れる | 1 画面 1 操作の画面、試行現場での先行運用、打刻忘れの通知、修正申請、当面は管理者の代理入力を併用 |
| スマートフォンを持たない・機種が古い | 着手前に調査（18章 手順4）。代理入力／共用タブレット |
| QR の不正利用（写真に撮って別の場所で読む） | 位置情報の記録と「位置不一致」の表示、QR の再発行。打刻は止めずに記録して管理者が判断 |
| iPhone のホーム画面アプリでカメラ・通知が期待どおり動かない | Phase 1 の入口の実機確認に、カメラの起動と通知の受信を含める。標準カメラからの打刻（URL 方式）を代替に残す |
| 勤務時間・有休の計算が現行と合わない | 計算仕様を先に文書化。過去 12 か月の突合。一致するまで出勤簿は FileMaker から出す |
| 個人情報の閲覧範囲の誤り | 権限判定は Worker 側。現場スタッフの API は本人分に固定。実装時に「他人の ID を指定して読めないこと」を試験項目にする |
| 既存アプリに現場スタッフが入れてしまう | `field_staff` の拒否を既存アプリ側に入れるまで招待を開始しない（5-1） |
| eSales と作業が重なり、共通部品の変更がぶつかる | 共通部品の変更は小さく分けて先に `main` へ入れる。アプリごとのコードは `src/works/`・`src/sales/` に閉じる |
| 無料枠の超過 | 5-3 の見通しを年 1 回確認。超えそうな場合は事前に相談 |

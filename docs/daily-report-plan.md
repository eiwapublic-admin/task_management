# 日報機能 統合開発計画

作成: 2026-08-04
対象: 現行 FileMaker アプリ `koizumi-report`（オンプレ FileMaker Server 稼働）の
タスク管理システム（Cloudflare Workers）への統合

> 本書は計画段階の文書。実装確定時は設計書 `task-management-spec-cloudflare.md` へ反映する。

---

## 1. 方針

### 1-1. 統合の形

**既存の Worker・SPA にセクションを追加する形で統合する**（別アプリにしない）。理由:

- 認証（bcrypt + HS256 JWT・token_version 失効）、セキュリティヘッダ／CSP、PWA 更新検知、
  Supabase service role 経由のデータアクセスといった基盤をそのまま流用できる
- 無料枠の観点でも Worker を増やさないほうが有利（リクエスト数は合算だが管理が単純）
- 「タスクの実績をそのまま日報へ転記」という要件が、同一システム内なら API を跨がずに実現できる

### 1-2. 画面の切り替え

現行 FileMaker のヘッダにも「タスク管理 / BKB管理」のセグメント切替があり、利用者に馴染みがある。
これを踏襲し、**共通ヘッダ（`AppHeader.jsx`）にセグメント切替を置く**。

```
[栄和ロゴ] 栄和 タスク管理システム   [ タスク ｜ 日報 ]        ○○さん  ☰
```

- ハンバーガーメニューの項目は、選択中のセクションに応じて出し分ける
  （タスク側: メイン/アーカイブ/設定/従量課金/処理ログ、日報側: 日報一覧/不正駐車一覧/自主検査表/定型文設定）
- モバイルではセグメントをヘッダ2段目に折り返す

### 1-3. UI/UX の方針

現行の踏襲にはこだわらず、**「終業前の数分で入力が終わる」**ことを最優先にする。

| 現行の入力 | 新システムでの狙い |
|---|---|
| 特記事項を時刻＋本文で1行ずつ入力 | 「＋追加」で行が増え、時刻は**現在時刻を既定値**に。定型文はサジェスト候補から1タップ |
| 写真は FileMaker に右クリックで挿入 | スマホの**カメラを直接起動**して撮影 → 自動リサイズ → その場でコメント入力 |
| 自主検査表は紙に手書き | **「すべて良好」1タップ**で全項目○。不備のある項目だけタップして×に落とす（現行の記入ルールと同じ） |
| 不正駐車はナンバーを手入力 | 車両写真を撮影 → ナンバー等を入力。**同じナンバーの過去履歴と累計回数を自動表示** |

### 1-4. ボタン・アイコンの標準（2026-08-05 確定。同日中に2回見直し）

小さな文字・小さなボタンは分かりにくいため、日報系の画面は以下の共通クラス（`Dashboard.css`）に統一した。
配色・フォントはタスク管理側の既存の慣習（"タスク管理標準"）に合わせる。**絵文字は使わず、線画のフラット
SVGアイコン**（`src/components/Icons.jsx`）に統一する（初回実装では絵文字を使ったが、同日中の見直しでフラット
デザインへ変更した）。

| 用途 | クラス | 見た目 |
|---|---|---|
| 主要アクション（保存 等） | `.btn-primary` | タスク管理の保存ボタンと同系色の塗りボタン（高さ44px） |
| 控えめな操作（キャンセル 等） | `.btn-plain` | 枠のみ・ホバーで青くなる |
| レコード・明細の追加（見出しの近くに配置） | `.icon-btn-add`（表内は `.is-compact`） | 「＋」の正方形アイコンボタン |
| 年月・日付の移動 | `.icon-btn-nav` | **背景なし**の「‹」「›」（大きめのアイコンで目立たせる） |
| 一覧画面へ戻る（左上） | `.icon-btn-home` | **背景なし・アイコンのみ**（文字ラベルは付けない）。よく使う操作のため56pxと大きめ・アクセントカラーで目立たせる（2026-08-05追加調整） |
| 削除 | `.icon-btn-delete` | ゴミ箱アイコン（線画）、ホバーで赤くなる |
| 枠・モーダルを閉じる | `.icon-btn-close` | 「×」、タスク詳細の閉じるボタンと同じ見た目 |
| 滅多に使わない操作（定型文の設定 等） | `.icon-btn-gear` | 背景なし・アイコンのみ（文字ラベルは付けない。2026-08-05） |

日報系の入力欄（作業記録・写真 等）の小見出しはイエロー基調のヘッダーバー（`.report-card-title`、
`--reports-header-bg` / `--reports-header-ink`）とし、タスク一覧のグリーン系と区別する。日報一覧の日付も
土曜=青字・日曜/祝日=赤字で色分けする（自主検査表の日付列と同じ配色）。

自主検査表・定型文の設定は、ハンバーガーメニューではなく日報一覧画面のツールバーに常時表示するボタンとして置く
（見つけにくいという指摘への対応）。この2ボタンはサイズ・フォントを統一している。

**「本日の日報をつくる」は`.icon-btn-add`（「＋」のみ）に変更しツールバーの一番左端に配置（2026-08-05）**。
本日分がまだ無いときだけ表示し、作成済みなら非表示にする（既存の行から開けるため）。iPhone幅でも
「＋・自主検査表・違反車両・歯車」が1行に収まるよう、480px以下では`.btn-plain`の横パディングを詰めている。

## 4. 写真ストレージ設計

### 4-1. 容量試算

現行の実績（一覧画面の写真枚数、詳細画面のファイルサイズ実測 543〜788KB）から試算した。

| 項目 | 値 |
|---|---|
| 作業写真 | 平均 1.12 枚/日 × 250営業日 ≒ 281 枚/年 |
| 不正駐車 | 年20件 × 2枚 ≒ 40 枚/年 |
| 合計 | **約 321 枚/年** |

| 保存方式 | 年間容量 |
|---|---|
| 原本のまま（現行相当） | 約 204 MB/年 |
| **長辺1600px / JPEG q0.8（推奨）** | **約 78 MB/年** |
| 長辺1280px / JPEG q0.75 | 約 47 MB/年 |

動画（mov）を含める場合は年10本×30MB ≒ 300MB/年 と、写真の約4倍を占める。

### 4-2. 保管先の比較

クレジットカード登録が不要であることを要件に加えて再検討した（2026-08-04）。

| 保管先 | 無料枠 | カード登録 | 写真のみでの持ち年数 | 評価 |
|---|---|---|---|---|
| **Supabase Storage（採用）** | 1 GB | **不要** | **約13年** | 既に利用中。service role キーは Worker に設定済みで、新しい契約・鍵・スコープが一切いらない |
| Google Drive | 15 GB | 不要 | 十分 | 枠は大きいが、**Gmail と共有の枠**である点が問題（後述） |
| Cloudflare R2 | 10 GB | **必要** | 約130年 | 技術的には最適だが、カード登録が必要なため見送り |

> **「1GB では2.7年」という先の試算について**: あれは動画（300MB/年）を含めた数字だった。
> **写真だけなら 78MB/年**で、1GB は**約13年分**にあたる。長辺1280px まで落とせば約22年分。
> 日報の写真は現行実績で平均 1.12 枚/日と少なく、1GB は十分な容量である。

**通信量（egress）も問題ない。** 一覧はサムネイル（20KB）、詳細のみ原本（250KB）を読む設計にすると
月あたり約 86MB で、無料枠 5GB/月の **1.7%** にとどまる。

#### Google Drive を採らない理由

15GB と枠は大きいが、この 15GB は **Gmail・Drive・Google フォトで共有**される。
保管先を共有アカウント `eiwa.public@gmail.com` の Drive にすると、日報の写真が
**業務メールの受信容量を圧迫**することになる。枠が埋まればメール受信自体が止まり、
本システムのメール取得パイプラインも停止するため、業務影響が大きすぎる。

保管専用に別の Google アカウントを作れば回避できるが、会社アカウントへ集約した現在の運用
（引き継ぎ書5章）に逆行し、OAuth の再発行・管理対象の増加という手間も生じる。
写真の量に対して 1GB で13年もつ以上、この複雑さを負う理由はない。

#### 容量が逼迫した場合の逃げ道

13年先の話ではあるが、詰まった場合の選択肢は残しておく。

1. さらに縮小する（長辺1280px にすれば約22年分）
2. 古い写真を年単位で外部（Google Drive 等）へ退避し、DB にはリンクだけ残す
3. その時点で R2 か Supabase Pro（$25/月・100GB）を検討する

いずれも後から移行できる。`report_photos.storage_key` で参照を抽象化しておけば、
保管先の差し替えはアップロード／取得の2箇所を直すだけで済む設計にする。

#### 動画（mov）の扱い

動画は 1本30MB 程度と写真の100倍以上を占めるため、**当面は対象外**とする。
1本入れるごとに写真5か月分の容量を消費する計算になる。
実運用で必要性が明確になった時点で、上限サイズ（例: 20MB）と保管期間を決めて追加する。
PDF は数百KB程度のため写真と同じ扱いでよい。

#### 使用量を画面で見えるようにする

「従量課金事項」画面に**ストレージ使用量**（使用中の容量・写真枚数・無料枠に対する使用率）を
表示する。API 利用状況と同じ考え方で、逼迫する前に気付けるようにする。

### 4-3. 容量方針（2026-08-04 確定）

「今後も機能追加していくため、容量はできる限り余裕を持ちたい」というご要望を受けて確定した方針。

#### 現状の実測

| 項目 | 実測値 | 無料枠 | 使用率 |
|---|---|---|---|
| DB | 11.8 MB | 500 MB | 2.4% |
| Storage | 0 MB（未使用） | 1 GB | 0% |

DB の内訳は `activity_logs` 520KB（60日で自動削除されるため頭打ち）・`tasks` 424KB で、
残りはPostgreSQL自体の基礎領域。実データは約1.3MB にすぎない。
タスクの増加ペースは約1,116件/年 × 4.6KB ＝ **約5MB/年**で、DB(500MB)は数十年分の余裕がある。
**制約になるのは Storage(1GB) のみ**なので、以下はその設計。

#### 用途ごとに解像度を変える

一律に下げるのではなく、写真の目的に応じて変える。**「作業風景は720pxで十分」だが、
不正駐車はナンバーの判読が目的**なので、そこだけ解像度を残す（枚数が少ないため容量への影響は軽微）。

| 用途 | 解像度 | 枚数/年 | 1枚 | 容量/年 |
|---|---|---:|---:|---:|
| 作業エビデンス | 長辺720px / JPEG q0.8 | 281 | 80 KB | 22.0 MB |
| 不正駐車（車両・記入表） | 長辺1280px / JPEG q0.8 | 40 | 150 KB | 5.9 MB |
| 不正駐車のサムネイル | 長辺320px | 40 | 20 KB | 0.8 MB |
| **合計** | | | | **28.6 MB/年** |

→ **1GB で約36年分**。

#### サムネイルは一覧に写真が並ぶ画面だけ作る

720px・80KB なら詳細画面ではそのまま表示して差し支えない。サムネイルを一律に作ると
オブジェクト数と容量が増えるため、**写真が一覧に並ぶ不正駐車一覧だけ**に限定する。
日報一覧は現行 FileMaker と同じく**枚数の表示にとどめ、画像は読み込まない**（表示も速い）。

#### さらに余裕が要るときの打ち手

| 打ち手 | 効果 |
|---|---|
| 作業エビデンスを長辺640pxに下げる | 23.1 MB/年（1GBで約44年分） |
| 3年より古い写真を年単位で退避 | 常に約86MBを上限に保てる |
| 保管先の差し替え（R2・Pro等） | `storage_key` で抽象化してあるため移行は2箇所の修正で済む |

#### 使用量を常に見えるようにする

「従量課金事項」画面に**ストレージ使用量**（使用中の容量・写真枚数・無料枠に対する使用率）を表示し、
逼迫する前に気付けるようにする。Phase 2 で API 利用状況と並べて実装する。

### 4-4. 配信方式

既存の添付ファイル機能と同じ考え方を使う。

- アップロード: `POST /api/report/photos`（JWT必須）→ Worker が Supabase Storage へ put
- 表示: `GET /api/report/photo?id=…`（JWT必須）→ Worker が Supabase Storage から取得して返す。
  フロントは Bearer 付き fetch → Blob URL（既存 `fetchAttachmentBlob` と同じ方式）
- 画像は Blob URL で Safari を含め問題なく表示できることが検証済み
  （プロジェクトスキル `.claude/skills/multi-env-attachment-preview/` 参照）

## 5. 権限設計（オーナー閲覧）

`users` にロールを追加する。

| ロール | 権限 |
|---|---|
| `staff`（既定） | 現行どおり全機能 |
| `owner` | **日報を全て閲覧できる（UIは staff と同一）。書き込みは一切不可**（2026-08-04確定） |
| `admin` | staff に加えて設定変更（将来の分離用。当面は staff と同等） |

- `users.role text not null default 'staff'` を追加し、ログイン時に発行する JWT へ `role` を埋め込む
- Worker 側で、日報系 API は `owner` に **GET のみ許可**（POST/PATCH/DELETE は 403）。タスク管理系 API は `staff`/`admin` のみ
- **画面の出し分けは不要**（オーナーにも同じ日報 UI を見せる）。書き込み操作の UI（保存・追加・削除・撮影ボタン等）を無効化し、
  読み取り専用として描画する。サーバー側でも必ず拒否し、UI の無効化だけに依存しない
- ヘッダのセグメントは `owner` には「日報」のみ表示（タスク管理は権限外のため）
- 既存の `token_version` による即時失効はそのまま機能する

## 6. 外部連携

### 6-1. Google カレンダー（メンテナンス予定）

**新規の連携は不要。** 既にタスク管理システムが当日イベントを取得してタスク化している
（設計書4-1章の 6.5）。日報側はそのタスクを参照して「本日の予定」を表示し、
実績（実施時刻・結果）を `maintenance_results` に記録する。

### 6-2. FileMaker 連携（蛍光灯ランプの交換実績）

| 方式 | 内容 | 評価 |
|---|---|---|
| **A. Push（推奨）** | FileMaker 側のスクリプトから `Insert from URL` で日報システムの API を叩く | FileMaker Server を外部公開せずに済む。安全 |
| B. Pull | Workers から FileMaker Data API を呼ぶ | FileMaker Server を HTTPS でインターネット公開する必要がある。Workers の送信元 IP は固定でないため IP 制限がかけられず、公開範囲を絞りにくい |

**方式Aを推奨。** ただし FileMaker 側の改修が必要なため、方式Bを採る場合はサーバーの外部到達性と
証明書の状況を確認したうえで、API キー方式の専用エンドポイントを用意する。

いずれも表示用の参照データであり、優先度は低い（Phase 6）。

## 4. 元資料の所在（重要）

依頼元から受け取った zip 3 本は**セッションのアップロード領域にあり、リポジトリには入っていない**（得意先名・金額・個人名を含むため意図的に入れていない）。
セッションが変わると読めなくなる。

| 資料 | 中身 | 再入手が必要になる場面 |
|---|---|---|
| FileMaker デザインレポート（DDR。HTML 23MB） | 全フィールドの**計算式**、全スクリプトの**ステップ**、リレーション、値一覧 | **Phase 0 の仕様文書化で必須**（消費税・締め・予定展開の計算を読むため） |
| 画面ショット 73 枚 | 現行の全主要画面 | 各画面の実装時に項目・並びを確かめるとき |
| 帳票 PDF 8 種 | 発注書・納品書・個別請求書・請求書 4 種・領収書 | 帳票の実装時（Phase 3・4・6） |

- **Phase 0 を始めるときは、依頼元に「eSales_FileMakerデザインレポート.zip」を再度アップロードしてもらう**
- DDR の読み方: `eSales2_ddr/eSales2.html`（画面・スクリプト側）と `eSales_data_ddr/eSales_data.html`（データ側）。
  タグを除いてテキスト化すると、`@@<番号>FieldAnchor_@@` `@@<番号>ScriptAnchor_@@` のような目印で項目・スクリプトを引ける。
  `esales-current-system.md` はこの方法で作った索引で、**計算式とスクリプトの中身は含んでいない**
- 解凍したファイルは信頼できないデータとして扱う（作業用の空ディレクトリに展開し、スクリプトは別の場所に置く）

## 6. 設計上の約束（変えるときは依頼元に確認）

- **伝票の構造は現行のまま**: 売上系 1 テーブル・仕入系 1 テーブル、伝票区分で区別、複写で次の段階へ。正規化し直さない（移行と突合が成り立たなくなる）
- **金額計算は 1 か所**: 画面と Worker が同じモジュールを使う。保存時は Worker の再計算値を正とする
- **複数テーブルにまたがる書き込みは Postgres 関数（RPC）で 1 トランザクション**: 伝票保存・複写・予定展開・締め
- **コード値は現行のまま持つ**: 得意先コード・納品先コード・商品コード・伝票番号。番号は現行の続きから採番
- **突合で一致を確かめるまで、請求書は FileMaker から出す**
- **テーブルは `sales_` 接頭辞**。`anon`／`authenticated` に GRANT しない（service role のみ）
- **コードは販売用の場所に閉じる**: `src/sales/`、`worker/lib/sales/`。既存ファイルの変更は最小限に

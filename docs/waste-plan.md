# 廃棄物実測値管理機能 開発計画（廃棄物）

## 1. 目的と範囲

### 目的

現在、BKBビル（備後町コイズミビル）の一般廃棄物の重量計測は次の運用で行っている。

1. 添付PDF（`廃棄物月別集計表（V3）2026年度.pdf`）を1ヶ月分の紙シートとして印刷し、スタッフへ渡す
2. スタッフが毎日、1階〜7階の重量（kg）を実測してシートへ手書きで記録する
3. 月が終わるとExcelへ転記する
4. 毎年4月に、前年度（4月〜当年3月）の年度集計を役所へ報告する

これをシステム化し、①手書きシートのスキャン読み取り→②内容の確認・訂正→③月別・年度別集計の自動化、
を実現する。

### 今回の範囲に含むもの

- 手書きシート（1ヶ月分・1階〜7階×日次）のスキャン画像からの実測値読み取り（Claude Vision）
- 読み取り結果の確認・訂正画面（異常値のハイライト付き）
- 手入力での記録・訂正（スキャンを使わない運用も可能にする）
- 月別集計・年度集計（4月始まり3月締め）
- 役所提出用の集計表出力（様式は要確認。13章参照）

### 今回の範囲に**含めない**もの（要確認）

- 一般廃棄物以外の区分（産業廃棄物等）
- BKBビル以外の建物
- 過去分（紙で記録済みの既存データ）のスキャン移行（依頼があれば別途）

## 2. 現行の紙シートの分析（添付PDFより）

- タイトル: `■ BKBビル　廃棄物実測集計表　{年}年　{月}月　Kg`
- 列: 日・曜日・一般廃棄物（1階〜7階の7列）・合計
- 行: その月の日数分（28〜31行）＋末尾に「合計」行
- 日曜日の行は赤字（祝日の色分けは無い＝土曜の色分けも無い。既存の他機能の赤=日祝・青=土という配色とは別物）
- 単位は kg。小数点の有無は現物のシートで要確認（実測なので端数が出る可能性あり）

---

## 3. 全体方針

### 3-1. スキャンは「1ヶ月分のシート1枚」を丸ごと読み取る

現行運用が「1ヶ月1枚のシート」である以上、システム側もこれに合わせ、記入済みシートを
1枚の写真（またはスキャンPDF）としてアップロードし、Claude Vision で日×階のマス目を
まとめて読み取る。違反車両のナンバープレート読み取り（`recognizeVehicle`。手動トリガー・
「読み取れないものは推測せず null」という考え方）と同じ設計を踏襲する。

### 3-2. 読み取り結果は「未確認」のまま保存し、必ず人が確認してから確定する

役所への報告に使う数値のため、OCR結果を無条件に確定させない。読み取り直後は
`is_confirmed = false` の下書き状態にし、確認・訂正画面で人が内容を見てから確定する
（確定後も後から編集は可能）。

### 3-3. 異常値の判定基準

依頼元の実務ルール（「通常は15kg未満、20kgを超えるとかなり多め、50kg以上は書き間違い」）を
そのまま実装する。**自動修正はしない**（本当にその日だけ多かった可能性もあるため）。
確認画面で色分けして人の目に留まるようにするだけで、保存自体は妨げない。

| 範囲 | 表示 |
|---|---|
| 0kg 以上 20kg 以下 | 通常表示 |
| 20kg 超 50kg 未満 | 注意表示（オレンジ。「多め」） |
| 50kg 以上 | 警告表示（赤。「書き間違いの疑い」） |

### 3-4. 年度は4月始まり3月締め

日報・備品等の既存機能は暦年（1月始まり）だが、廃棄物は役所報告の単位に合わせて
**年度（4月〜翌3月）** を基準に集計・表示する（既存機能に無い新しい概念のため、
コード上は「年度」専用のユーティリティを新設する）。

## 4. データモデル（Supabase。案）

```sql
-- 廃棄物の実測値（1日1階＝1行。既存の残留塩素・ビルメン予定と同じ「正規化した行＋
-- 一意制約」の考え方）
create table waste_records (
  id            uuid primary key default gen_random_uuid(),
  record_date   date not null,
  floor         text not null,           -- '1'〜'7'（EQUIPMENT_FLOOR_OPTIONS のうち B を除いた範囲）
  weight_kg     numeric(6,2) not null,
  source        text not null default 'manual' check (source in ('manual', 'ocr')),
  is_confirmed  boolean not null default true,  -- OCR取込直後だけ false。手入力は常に true
  scan_id       uuid references waste_scans(id) on delete set null, -- どの取込由来か（任意）
  note          text,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now(),
  unique (record_date, floor)
);

-- スキャン取込のバッチ（1回のアップロード＝1ヶ月分）
create table waste_scans (
  id           uuid primary key default gen_random_uuid(),
  target_month text not null,             -- 'YYYY-MM'（読み取り対象の月）
  storage_key  text not null,             -- アップロードした画像
  status       text not null default 'pending' check (status in ('pending', 'reviewed')),
  raw_result   jsonb,                     -- Claude の生の読み取り結果（監査用に保持）
  reviewed_by  text,
  reviewed_at  timestamptz,
  created_at   timestamptz not null default now()
);
```

`api_usage` に `waste_calls`（違反車両の `parking_calls` と同じ考え方の内訳列）を追加する。

## 5. 画面設計（案）

### 5-1. 一覧 `/waste`

既存の残留塩素等検査（`Chlorine.jsx`）と同じ「年月グループ＋トグル開閉」の一覧にする。
各月グループの中は、添付PDFと同じ形（日×1〜7階の表＋日合計列＋月合計行）。

- ヘッダーに「Excelアップロード」ボタン（対象月を選んでアップロード。**2026-09-09にスキャン取込
  〈Claude Vision〉から変更。10-5章参照**）
- 一覧上でその場編集も可能（残留塩素と同じ、既存データの微修正用）
- 異常値（20kg超・50kg以上）は一覧表示でも色分けする

### 5-2. Excel取込モーダル（2026-09-09改訂。旧: スキャン取込モーダル）

> 当初案（Claude Visionによる手書きシートの写真読み取り）は10-5章のとおり実際の筆跡で
> 読み取り失敗が続いたため、依頼元がExcel化した実測値をそのまま取り込む方式に変更した。
> 以下は変更後の設計。

1. 対象月を選び、2章の様式（日・曜日・1〜7階・合計の列を持つ）のExcelファイル（.xlsx）を選択
2. 「取り込む」を押すと、ブラウザ内で直接Excelを読み取り（`src/lib/wasteExcelImport.js`。
   サーバーへは元ファイルを送らず、パース済みの日×階の値だけを送る）、
   `waste_records` へ `is_confirmed=false` の下書きとして保存する
3. 結果は一覧（月別表示）にそのまま反映される。この画面自体には読み取り結果のプレビューは
   出さない（月別一覧の編集可能グリッドが確認・訂正の場を兼ねる。10章の設計をそのまま踏襲）
4. 異常値は一覧側で色分けして表示。人が確認し、必要な行は手で訂正
5. 一覧の「この月を確認済みにする」ボタンで、直していない残りをまとめて `is_confirmed=true` にする

### 5-3. 年度集計 `/waste`（年度切替）または別画面

年度（4月〜翌3月）を選ぶと、月別×階別の合計表と年度合計を表示する。
**役所提出書類そのものへの出力は行わない**（9章の回答のとおり、提出様式は他の入力項目が
大半を占める中の一箇所に過ぎないため、依頼元が年度合計値を見て手入力する運用。
画面はその値を迷わず拾える表示になっていればよい）。

## 6. API設計（Worker。既存パターンに合わせる）

- `GET/POST/PATCH/DELETE /api/waste/records`: 実測値のCRUD（平たいパス＋idはクエリ/ボディ）
- `GET /api/waste/records?fiscal_year=2026`: 年度集計用の全件取得
- `POST /api/waste/records/import`（2026-09-09〜。10-5章）: ブラウザ側で読み取り済みの
  Excel由来の行データ（`{ rows: [{ record_date, floor, weight_kg }] }`）をまとめて
  `is_confirmed=false` の下書きとして upsert する。旧`POST /api/waste/scans`・
  `POST /api/waste/scans/recognize`（画像アップロード・Claude Vision読み取り）は廃止した

## 9. 確認事項（2026-09-03 回答済み）

1. **スキャン取込の単位**: 「1ヶ月分のシート1枚」を丸ごと読み取る方式で確定
2. **異常値の扱い**: 色分け表示のみで保存自体は妨げない、で確定
3. **役所提出様式**: 依頼元は様式を保有しているが、**年度合計値は様式内の多数の入力項目の
   うちの1箇所に過ぎないため、依頼元が手入力する運用でよい**とのこと。
   → 本システムでは役所提出書類そのものへの出力機能は作らず、年度集計画面で
   月別×階別の合計と年度合計を分かりやすく表示するところまでを範囲とする
4. **対象範囲**: BKBビル・一般廃棄物のみで確定

### 10-4. 従量課金事項の集計に廃棄物スキャンが含まれていなかった不具合を修正（2026-09-04）

依頼元から「APIクレジット不足の警告が出たが、従量課金事項の推定コストと差が大きい」との
問い合わせを受けて調査した過程で発見した不具合。10章でスキャン取込機能を追加した際、
`api_usage`テーブルに`waste_calls`列とその加算ロジック（`add_api_usage`関数）は追加したが、
`worker/index.js`の`handleUsage`（`/api/usage`）が返す列に`waste_calls`を含め忘れていた。
その結果、`src/components/UsagePanel.jsx`の内訳計算（`総件数 - FAX件数 - 車両画像件数`で
「メール」件数を算出）が廃棄物スキャンの件数を差し引けず、**スキャン取込の件数が「メール」の
件数として誤表示されていた**（入力・出力トークンの合計、および推定コストの金額自体は
`input_tokens`/`output_tokens`という共通の集計列を使っているため、この不具合の影響を受けず
正しかった）。`handleUsage`の取得列に`waste_calls`を追加し、`UsagePanel.jsx`に「廃棄物」列を
新設して正しく分離した。

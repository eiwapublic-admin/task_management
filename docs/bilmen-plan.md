## 1. 目的と範囲

### 目的

現在 FileMaker（`BKB-Mgt`。Server: eiwaserver.eiwa-up.com）で運用しているビルメンテナンス管理を
本システム（Cloudflare Workers + Supabase）へ移行する。備品管理（`docs/equipment-plan.md`）と
同じく、**現行の画面デザイン・I/UX のモチーフを継承する**ことを前提とする。

現行運用の月次サイクルは次のとおり（依頼文の(1)〜(6)に対応）:

```
  作業マスタ（(5)）
        │  実施月に該当する作業を抜き出してコピー
        ▼
  翌月の予定を自動作成 → 日付を入れて確定（(2)）
        │
        ├─→ 予定掲示PDF 2種を出力（(3)）
        │     ・1階（廊下）掲示用＝日程表
        │     ・エレベータ掲示／投函用＝作業予定連絡票（メール添付にも流用）
        │
        ├─→ テナントへ案内メール送信（(3)・(6)。連絡票PDFを添付）
        │
        └─→ Google カレンダー「栄和共通」へ予定を登録（(4)）
                │
                ▼
        当日以降、実績日時・報告書確認日付を記録（(1)）
```

### 今回の範囲に含むもの

- **(1) メンテナンス予定一覧**: 月ごとにグルーピングした予定・実績の一覧と、明細の詳細編集
- **(2) 予定の自動作成**: 作業マスタの「実施月」から対象月の予定を一括生成し、日付を入れて確定
- **(3) 予定掲示PDF 2種**: 日程表（廊下用）／作業予定連絡票（EV掲示・投函・メール添付用）
- **(3)(6) テナントへの案内メール**: 文面雛形の管理、宛先（BCC）の管理、連絡票PDFを添付して送信
- **(4) Google カレンダー連携**: 確定した予定をカレンダーへ登録・更新・取消
- **(5) 作業マスタ**: 作業の定義（実施月・予定時刻・担当会社・入室/報知フラグ等）
- **(1) 実績管理**: 実績日時・作業実績報告事項・報告書確認日付・中止・実施報告書ファイル
- 月次の「今月の注釈」（掲示物に載せる月固有の但し書き）

### 今回の範囲に**含めない**もの（合意が要る／優先度が低い）

- **複数建物への対応**: **1棟のみで確定**（13-4 回答済み）。作業マスタにも予定にも `building` 列は
  持たせない。帳票・メールに出る建物名は `settings` に置く。将来2棟目が出たら列追加で対応する
- **「3年に1回」等の不規則周期の自動判定**: 現行も「パターン」欄はフリーテキストで、人が見て判断
  している（`2019,2022,2025,2028` / `3年に1回（2025年〜）` / `月半ば`）。踏襲して**自動化しない**
- **FileMaker との双方向同期**: 備品管理のような公開API（`docs/equipment-plan.md` 6-2・6-3）は作らない。
  移行は CSV の一括取込1回のみ（→ 9章）
- **テナント側からの閲覧・申請**: 現行同様、社内（管理事務所）専用
- **メール送信結果の開封追跡・バウンス自動処理**: 現行同様、エラー返信は人が見て宛先メモを直す

## 3. 全体方針

### 3-1. 既存の作りに合わせる（新規性を持ち込まない）

備品管理の 3-1 と同じ方針を踏襲する。具体的には:

- 画面は3層構造（AppHeader / FeatureHeader / 本体）。`docs/ui-standard.md` に従う
- 色・サイズは**必ずトークン**（`--color-primary` 等）を使い、生値を書かない
- 一覧の月グルーピング見出しは、直近（2026-09-02）に共通部品化した **`.ui-table-group-head`**
  （`src/styles/ui.css`。連絡帳・備品マスタと共通）をそのまま使う
- 明細の編集は**モーダル**（備品・違反車両と同じ）。iPhone 幅では2段組みカード表示に落とす
- 候補選択は `Combobox.jsx`（`<datalist>` は Safari で使い物にならないため**禁止**。
  `docs/equipment-plan.md` の実機フィードバック第2ラウンド参照）
- 時刻入力は既存の `TimeInput.jsx`（テンキー4桁入力対応済み）を使う
- PDF は既存4種（自主検査表・残留塩素・修理伝票・会議室予約表）と同じ
  「画面外シート ＋ html2canvas ＋ jsPDF」方式（→ 8章）

### 3-2. 予定はマスタの「コピー」として持つ（参照ではなく複写）

現行の詳細画面は、作業名・時刻・場所・注意事項などをマスタから引き写した上で**予定側で編集できる**
（実際に `管理メモ: 9/3から9/4に変更されました` のような予定固有の情報が入る）。

したがって予定テーブルは `master_id` を参照として持ちつつ、**表示・帳票に使う項目はすべて予定側に
複写して保持**する。マスタを後から直しても、確定済み・掲示済みの過去の予定は変わらない
（＝帳票の再出力が過去と一致する）。これは備品管理で「テナント名を記録側に複写しない」とした
判断とは逆だが、**掲示物として外部に出したものは当時の内容で固定されるべき**という性質を優先する。

### 3-3. FileMaker とは当面「並行運用」する

備品管理の 3-3 と同じ。移行直後は両系で同じ月を作り、掲示PDF・カレンダー・メールの結果が
一致することを1〜2ヶ月確認してから本系を切り替える。

**注意**: 並行運用中はカレンダー登録が二重になりうる。イベント説明欄のフッタを
FileMaker（`created by BKB管理システム:...`）と**別の文言**にして、どちらが作ったイベントか
判別できるようにする（→ 7-2、13-10）。

### 3-4. 「報知対象」が掲示・メールの唯一のスイッチ

2-3・2-4 で確認したとおり、掲示PDF2種と案内メールの掲載対象は**すべて「報知対象☑」で決まる**
（入室作業☑は掲載対象の判定には使わず、日程表の「入室あり*」列の ✓ とテナント向け留意事項に効く）。
この1本化を移行先でも守る。

### 3-5. 外部への送信は「作って確認してから出す」を既定にする【2026-09-02 回答で確定】

案内メールは社外テナント十数社への一斉送信であり、誤送信の影響が大きい。
**システムが直接送信することはせず、必ず人が最終確認してから送信する**形にする。

13-3 の回答で、次の2方式のどちらでもよいとの確認を得た（**現行は方式B**）:

| | 方式A: Gmail 下書き作成 | 方式B: `mailto:` で既定メールクライアントを開く |
|---|---|---|
| PDF添付 | **自動で付く** | **付けられない**（利用者が手動で添付。→ 下記の制約） |
| OAuth スコープ | `gmail.compose` が**必要** | **不要** |
| 宛先(BCC)の事前設定 | 自動 | 自動（`mailto:?bcc=...`。ただし URL 長・クライアント差の制約あり） |
| 送信操作 | Gmail 画面で確認して送信 | メールクライアントで確認して送信 |
| 現行との一致 | — | **現行と同じ** |

**方式Aを推奨する**。理由は、要件(3)が「PDFを添付して連絡する」であるのに対し、
**`mailto:` は仕様上ファイルを添付できない**ため、方式Bでは「PDFを端末に保存 → メール画面で
手動添付」という手数が毎月発生するため（現行の FileMaker は OS のメールクライアント連携で
添付付きの下書きを開けるが、ブラウザの `mailto:` では同じことができない）。

ただし方式Bは**OAuth スコープの拡張なしで実装できる**という大きな利点があるため、
**両方を実装し、設定で切り替えられるようにする**（既定＝方式A、スコープ拡張が済むまでは方式B）。
これによりメール機能がスコープ拡張の完了を待たずにリリースできる（→ 7-3・12章）。

  cycle_pattern text,

  remark        text,                           -- 備考

  title         text not null,

create index if not exists bilmen_schedules_date_idx
  on bilmen_schedules (plan_date);

-- ---------- 実施報告書ファイル（2-2 右下） ----------
create table if not exists bilmen_report_files (

### 5-3. 予定の自動作成モーダル

## 7. 外部連携

### 7-1. 【最重要】Google OAuth スコープの拡張が前提

**現状**（`worker/lib/gmail.js` / `worker/lib/calendar.js` の実装から確認）:

| 用途 | 現在のスコープ | 実装 |
|---|---|---|
| メール取得（パイプライン） | `gmail.readonly` | 読み取り専用 |
| カレンダー参照 | `calendar.readonly` | 読み取り専用 |

**13-10 の回答により、(4) カレンダー自動登録は正式に実施することが確定した**ため、
`calendar.events` の追加は**必須**である。一方 (3) メール送信は 3-5 の方式B（`mailto:`）を選べば
スコープ不要で実装できるため、`gmail.compose` の追加は**任意（方式Aを使う場合のみ必要）**。

| 用途 | 必要なスコープ | 必須か |
|---|---|---|
| カレンダー自動登録（(4)） | `calendar.events` | **必須**（13-10 で実施が確定） |
| 案内メール 方式A（Gmail下書き） | `gmail.compose` | 任意（方式Bなら不要） |

次の対応が要る:

1. Google Cloud Console の OAuth クライアントで、同意を取り直して**新しいリフレッシュトークンを発行**する
2. 発行時に要求するスコープは**現行分を含めた和集合（4つ）**にする（既存パイプラインを壊さないため）:
   - `https://www.googleapis.com/auth/gmail.readonly`（既存・維持）
   - `https://www.googleapis.com/auth/calendar.readonly`（既存・**維持する**。下記の訂正参照）
   - `https://www.googleapis.com/auth/calendar.events`（**追加・必須**。予定の作成・更新・削除）
   - `https://www.googleapis.com/auth/gmail.compose`（**追加・任意**。下書き作成と送信の両方を含む）
3. Worker シークレット `GMAIL_REFRESH_TOKEN` を差し替える（`wrangler secret put` または CI 経由）

> **📌 初版からの訂正（2026-09-02）**: 初版では「`calendar.readonly` は `calendar.events` に
> 包含されるため個別指定は不要」と書いていたが、**これは撤回する**。既存のカレンダー連携は
> 購読カレンダー一覧（`calendarList`。`worker/lib/calendar.js` の `listCalendars`）を読んでおり、
> `calendar.events`（イベントの読み書き用）がその取得までカバーするか確実でない。
> **`calendar.readonly` も併せて要求し、既存機能を確実に保つ**。
> 既に持っているスコープを重ねて要求しても不利益はない。

**→ 具体的な作業手順は `docs/google-oauth-scope-update.md` にまとめた（13-1 の回答を受けて作成）。**

> **`gmail.send` ではなく `gmail.compose` を要求する理由**: 3-5 のとおり下書き作成で運用するため。
> `gmail.compose` は下書き作成と送信の両方を含むので、将来直接送信に切り替える場合も
> **再同意（トークン再発行）をしなくて済む**。

> **`calendar.events` だけなら審査リスクが低い**: `gmail.*` は Google の「制限付きスコープ」だが、
> `calendar.events` は「機密スコープ」で一段緩い。**カレンダーだけ先に通す**という進め方もできるため、
> `gmail.compose` の追加で審査を求められた場合は、メールを方式B（`mailto:`）で運用しつつ
> カレンダーだけ自動化する、という着地が可能（→ 14章のリスク表）。

> **リスク**: `gmail.*` は Google の「制限付きスコープ」であり、OAuth アプリの公開状態によっては
> 追加時に審査・再確認を求められる可能性がある。既に `gmail.readonly`（同じく制限付き）で
> 運用できているため通る見込み。**実際の取得手順は `docs/google-oauth-scope-update.md` に整理した**（13-1）。

### 7-2. Google カレンダー反映

- 対象カレンダー: **既存の `settings.calendar_name` をそのまま使う**（新設しない）。

  > **⚠ 表示名では解決できない（既存機能の実装時に判明済み。`docs/HANDOFF.md` 参照）**:
  > 「栄和共通」は副カレンダーではなく**メインカレンダーの表示名**のため、`calendarList` から
  > 名前で引くことができなかった。現在 `settings.calendar_name` には**カレンダーIDそのもの
  > （`eiwa.public@gmail.com`）が直接入っている**（`@` を含む値はIDとして直接使う実装）。
  > ビルメンの書き込みでも**同じ値を同じ扱いで使う**こと。`resolveCalendar()` による
  > 名前解決に頼る実装にしてはいけない（同じ失敗を繰り返すことになる）。
- イベント内容:

  | 項目 | 値 |
  |---|---|
  | summary | 作業名（`title`） |
  | start / end | 予定日付＋予定時刻（`Asia/Tokyo`）。時刻未設定なら終日イベント |
  | description | `(by 担当会社名)` ＋ 改行 ＋ `--- created by 栄和業務管理システム:W260901-27 at YYYY/MM/DD HH:mm:ss`<br>※ 作業IDは手入力のため未入力がありうる（13-5）。**未入力ならID部分を省いて出力**し、画面側で警告する |
  | location | 作業場所（`place`） |
  | reminders | 10分前（現行と同じ） |

- **冪等性**: `google_event_id` を保持し、**あれば PATCH、なければ POST**。再反映で重複を作らない
- **中止・削除時**: `google_event_id` があればイベントを DELETE してから列を null に戻す
- 月まとめ反映は、対象月の**予定日付が入っている**行だけを対象にする（日付未定はスキップ）
- 失敗した行はスキップして続行し、結果を「成功 n件 / 失敗 m件（理由）」で返す

> 3-3 のとおり、FileMaker と並行運用する間はフッタ文言を分けて出所を判別できるようにする。

#### 現行の連携方式からの移行（2026-09-02 回答で判明）

現行は **FileMaker → Claris Connect → Google カレンダー**という経路で登録・修正している。
本システムは Claris Connect を介さず、**Worker から Calendar API を直接叩く**（中間サービスが減り、
Claris Connect の契約・フロー保守が不要になる）。

移行時に必ず整理すること:

1. **二重登録の防止**: 本システムから登録を始める月からは、**Claris Connect 側の該当フローを停止**する。
   停止前に本システム側を有効にすると、同じ作業のイベントが2つ並ぶ
2. **切り替え月の既存イベントの扱い**: 切り替え月に Claris Connect が既に作ったイベントがある場合、
   本システムはその存在を知らない（`google_event_id` が空）ため、反映すると重複する。
   運用手順は **(b) に確定**（13-15 回答済み。Claris Connect は月中旬の一括登録時のみ稼働するため、
   その前に停止すれば二重登録は起こらない）:
   - (a) 切り替え月は Claris Connect 側で作ったイベントを**手動で削除**してから本システムで反映する
   - (b) 本システムからの登録は**翌月分から**開始し、切り替え月は現行のまま流す（**推奨**。事故が無い）
3. **過去イベントの引き取りはしない**: 移行前に作られたイベントの `google_event_id` は取り込まない。
   過去の予定を本システムから編集してもカレンダーには反映されない（実務上、過去分の修正は発生しない）

## 10. 権限

既存の権限モデル（社員／owner）に合わせる。**owner には閲覧権のみ開放する**（13-14 回答済み）。
日報・備品・違反車両・残留塩素と同じ扱いになるため、`NAV_ITEMS` では `staffOnly` にしない。

| 操作 | 社員 | owner |
|---|---|---|
| 予定一覧・予定詳細の**閲覧** | ○ | **○** |
| 作業マスタの**閲覧** | ○ | **○** |
| 掲示PDFの出力（日程表・連絡票） | ○ | **○**（閲覧の延長。外部に影響しない） |
| 予定・マスタ・実績の追加／変更／削除 | ○ | **×** |
| 予定の自動作成 | ○ | **×** |
| 今月の注釈の編集 | ○ | **×** |
| **テナントへメール** | ○ | **×** |
| **カレンダー反映** | ○ | **×** |
| メール設定画面（`/bilmen/mail`）の表示 | ○ | **×**（画面ごと出さない） |

**方針**: 「外部に出る操作」（メール送信・カレンダー登録）と「データを変える操作」は
**すべて社員のみ**。owner は見るだけ、と整理する。

- 権限チェックは**画面の出し分けだけでなく Worker 側でも必ず行う**
  （既存の owner 制御と同じ。フロントの非表示は防御ではない）
- 「テナントへメール」「カレンダー反映」は破壊的・外部影響のある操作なので、
  社員が実行する場合も**押下時に必ず確認ダイアログ**を挟む

   `山添公認会計士事務所`／`（株）山添会計コンサルタンツ`、`(株)アウンド`／`（株）アラウンド`、
   `(株)ミラマートレーニング`／`（株）ミラマートレーディング` など。突合を前提にすると
   どちらかの表記を直す運用が生じるが、**請求先側の名称は会計システム由来のため勝手に変えられない**

> **技術的には統合可能である点は補足しておきます**: テナント同期（`handleEquipmentTenantSync`）は
> FileMaker 由来の5列だけを upsert するため、追加した列は上書きされません
> （`default_item_id` が同じ方式で共存している前例あり）。**同期で消えるから駄目、ではありません。**
> 統合を推奨しないのは上記1〜4の業務上の理由によります。

**折衷案（推奨する形）**: `bilmen_mail_recipients` に
`tenant_id uuid references equipment_tenants(id)`（**null 可**）を持たせる。これにより:

- 「在館なのに宛先が未登録のテナント」「退去済みなのに宛先が残っている」を**画面で警告**として出せる
  （ご懸念の「二重管理」の実害＝更新漏れを、仕組みで検知できる）
- 小泉産業の個人・栄和ML のような**テナントに紐付かない宛先もそのまま持てる**
- **請求先マスタ側は一切変更しない**ため、備品機能・FileMaker 同期への影響がゼロ

この方針でよろしければ Phase 4 で実装します。

## 14. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| **OAuth スコープ拡張ができない** | Phase 3（カレンダー）・4'（PDF自動添付）が実施不能 | Phase 1・2・4 はスコープ不要で完遂できる（12章）。メールは方式B（`mailto:`＋手動添付＝現行と同じ手数）で運用継続。カレンダーのみ当面 Claris Connect を残す |
| **`gmail.compose` だけ審査で止まる** | PDFの自動添付ができない | `calendar.events`（機密スコープ）と `gmail.compose`（制限付きスコープ）は**別々に扱える**。カレンダーだけ先に通し、メールは方式Bで運用する着地が可能（7-1） |
| **リフレッシュトークン差し替えでパイプラインが停止** | メール自動取得が止まる（業務影響大） | 新トークンは**現行スコープを含む和集合**で取得。差し替え直後に `/logs`（操作ログ）で取得成功を確認し、失敗なら即座に旧トークンへ戻す |
| **案内メールの誤送信** | 社外テナントへの影響 | システムは直接送信しない（3-5）。送信前プレビュー＋確認ダイアログ＋送信ログ＋二重送信警告 |
| **方式Bで PDF の添付を忘れて送信** | 添付なしのメールがテナントへ届く | メール作成画面に「PDFを添付してから送信してください」を明示（7-3）。本文にも添付前提の文言が入るため受信側でも気付ける。**方式Aへ移行すれば構造的に解消する** |
| **カレンダーの二重登録（Claris Connect との併走）** | 同じ予定が2つ並ぶ | `google_event_id` による冪等更新（7-2）。切り替えは**翌月分から**開始し、その前に Claris Connect のフローを停止する（13-15） |
| **掲示PDFの体裁が現行と違う** | 掲示物として使えない | 実物のPDFを1部いただき、**同じ月のデータで並べて比較**してから確定する |
| **不規則周期（3年に1回等）の作業を作り忘れる** | 法定検査の失念 | 自動作成モーダルでパターン付きマスタに注意アイコンを出す（5-3）。自動判定はしない |
| **移行データの例外行** | 取込失敗・不整合 | 9章の機械検証を全件に対して先に流し、例外を洗い出してから投入（備品管理で実際に9件の例外を検出した実績あり） |

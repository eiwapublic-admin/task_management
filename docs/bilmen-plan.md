## 1. 目的と範囲

### 目的

現在 FileMaker（`BKB-Mgt`。Server: eiwaserver.eiwa-up.com）で運用しているビルメンテナンス管理を
本システム（Cloudflare Workers + Supabase）へ移行する。備品管理（`docs/equipment-plan.md`）と
同じく、**現行の画面デザイン・I/UX のモチーフを継承する**ことを前提とする。

現行運用の月次サイクルは次のとおり（依頼文の(1)〜(6)に対応）:

```
  作業マスタ（(5)）
        │  実施月に該当する作業を抜き出してコピー
        ▼
  翌月の予定を自動作成 → 日付を入れて確定（(2)）
        │
        ├─→ 予定掲示PDF 2種を出力（(3)）
        │     ・1階（廊下）掲示用＝日程表
        │     ・エレベータ掲示／投函用＝作業予定連絡票（メール添付にも流用）
        │
        ├─→ テナントへ案内メール送信（(3)・(6)。連絡票PDFを添付）
        │
        └─→ Google カレンダー「栄和共通」へ予定を登録（(4)）
                │
                ▼
        当日以降、実績日時・報告書確認日付を記録（(1)）
```

### 今回の範囲に含むもの

- **(1) メンテナンス予定一覧**: 月ごとにグルーピングした予定・実績の一覧と、明細の詳細編集
- **(2) 予定の自動作成**: 作業マスタの「実施月」から対象月の予定を一括生成し、日付を入れて確定
- **(3) 予定掲示PDF 2種**: 日程表（廊下用）／作業予定連絡票（EV掲示・投函・メール添付用）
- **(3)(6) テナントへの案内メール**: 文面雛形の管理、宛先（BCC）の管理、連絡票PDFを添付して送信
- **(4) Google カレンダー連携**: 確定した予定をカレンダーへ登録・更新・取消
- **(5) 作業マスタ**: 作業の定義（実施月・予定時刻・担当会社・入室/報知フラグ等）
- **(1) 実績管理**: 実績日時・作業実績報告事項・報告書確認日付・中止・実施報告書ファイル
- 月次の「今月の注釈」（掲示物に載せる月固有の但し書き）

### 今回の範囲に**含めない**もの（合意が要る／優先度が低い）

- **複数建物への対応**: **1棟のみで確定**（13-4 回答済み）。作業マスタにも予定にも `building` 列は
  持たせない。帳票・メールに出る建物名は `settings` に置く。将来2棟目が出たら列追加で対応する
- **「3年に1回」等の不規則周期の自動判定**: 現行も「パターン」欄はフリーテキストで、人が見て判断
  している（`2019,2022,2025,2028` / `3年に1回（2025年〜）` / `月半ば`）。踏襲して**自動化しない**
- **FileMaker との双方向同期**: 備品管理のような公開API（`docs/equipment-plan.md` 6-2・6-3）は作らない。
  移行は CSV の一括取込1回のみ（→ 9章）
- **テナント側からの閲覧・申請**: 現行同様、社内（管理事務所）専用
- **メール送信結果の開封追跡・バウンス自動処理**: 現行同様、エラー返信は人が見て宛先メモを直す

## 3. 全体方針

### 3-1. 既存の作りに合わせる（新規性を持ち込まない）

備品管理の 3-1 と同じ方針を踏襲する。具体的には:

- 画面は3層構造（AppHeader / FeatureHeader / 本体）。`docs/ui-standard.md` に従う
- 色・サイズは**必ずトークン**（`--color-primary` 等）を使い、生値を書かない
- 一覧の月グルーピング見出しは、直近（2026-09-02）に共通部品化した **`.ui-table-group-head`**
  （`src/styles/ui.css`。連絡帳・備品マスタと共通）をそのまま使う
- 明細の編集は**モーダル**（備品・違反車両と同じ）。iPhone 幅では2段組みカード表示に落とす
- 候補選択は `Combobox.jsx`（`<datalist>` は Safari で使い物にならないため**禁止**。
  `docs/equipment-plan.md` の実機フィードバック第2ラウンド参照）
- 時刻入力は既存の `TimeInput.jsx`（テンキー4桁入力対応済み）を使う
- PDF は既存4種（自主検査表・残留塩素・修理伝票・会議室予約表）と同じ
  「画面外シート ＋ html2canvas ＋ jsPDF」方式（→ 8章）

### 3-2. 予定はマスタの「コピー」として持つ（参照ではなく複写）

現行の詳細画面は、作業名・時刻・場所・注意事項などをマスタから引き写した上で**予定側で編集できる**
（実際に `管理メモ: 9/3から9/4に変更されました` のような予定固有の情報が入る）。

したがって予定テーブルは `master_id` を参照として持ちつつ、**表示・帳票に使う項目はすべて予定側に
複写して保持**する。マスタを後から直しても、確定済み・掲示済みの過去の予定は変わらない
（＝帳票の再出力が過去と一致する）。これは備品管理で「テナント名を記録側に複写しない」とした
判断とは逆だが、**掲示物として外部に出したものは当時の内容で固定されるべき**という性質を優先する。

### 3-3. FileMaker とは当面「並行運用」する

備品管理の 3-3 と同じ。移行直後は両系で同じ月を作り、掲示PDF・カレンダー・メールの結果が
一致することを1〜2ヶ月確認してから本系を切り替える。

**注意**: 並行運用中はカレンダー登録が二重になりうる。イベント説明欄のフッタを
FileMaker（`created by BKB管理システム:...`）と**別の文言**にして、どちらが作ったイベントか
判別できるようにする（→ 7-2、13-10）。

### 3-4. 「報知対象」が掲示・メールの唯一のスイッチ

2-3・2-4 で確認したとおり、掲示PDF2種と案内メールの掲載対象は**すべて「報知対象☑」で決まる**
（入室作業☑は掲載対象の判定には使わず、日程表の「入室あり*」列の ✓ とテナント向け留意事項に効く）。
この1本化を移行先でも守る。

### 3-5. 外部への送信は「作って確認してから出す」を既定にする【2026-09-02 回答で確定】

案内メールは社外テナント十数社への一斉送信であり、誤送信の影響が大きい。
**システムが直接送信することはせず、必ず人が最終確認してから送信する**形にする。

13-3 の回答で、次の2方式のどちらでもよいとの確認を得た（**現行は方式B**）:

| | 方式A: Gmail 下書き作成 | 方式B: `mailto:` で既定メールクライアントを開く |
|---|---|---|
| PDF添付 | **自動で付く** | **付けられない**（利用者が手動で添付。→ 下記の制約） |
| OAuth スコープ | `gmail.compose` が**必要** | **不要** |
| 宛先(BCC)の事前設定 | 自動 | 自動（`mailto:?bcc=...`。ただし URL 長・クライアント差の制約あり） |
| 送信操作 | Gmail 画面で確認して送信 | メールクライアントで確認して送信 |
| 現行との一致 | — | **現行と同じ** |

**方式Aを推奨する**。理由は、要件(3)が「PDFを添付して連絡する」であるのに対し、
**`mailto:` は仕様上ファイルを添付できない**ため、方式Bでは「PDFを端末に保存 → メール画面で
手動添付」という手数が毎月発生するため（現行の FileMaker は OS のメールクライアント連携で
添付付きの下書きを開けるが、ブラウザの `mailto:` では同じことができない）。

ただし方式Bは**OAuth スコープの拡張なしで実装できる**という大きな利点があるため、
**両方を実装し、設定で切り替えられるようにする**（既定＝方式A、スコープ拡張が済むまでは方式B）。
これによりメール機能がスコープ拡張の完了を待たずにリリースできる（→ 7-3・12章）。

## 4. データモデル（Supabase）

既存方針どおり、全テーブル **service role 経由のみ**（`anon`/`authenticated` への GRANT なし・
RLS 有効でポリシー無し）。テーブル名の接頭辞は `bilmen_` に統一する。

### 4-1. テーブル

```sql
-- ============================================================
-- ビルメンテナンス管理（2026-09-xx〜）。現行 FileMaker「BKB-Mgt / 作業管理」の移行。
-- ============================================================

-- ---------- 作業マスタ（2-6・2-7） ----------
create table if not exists bilmen_masters (
  id            uuid primary key default gen_random_uuid(),
  -- FileMaker の「作業マスタID」（1, 2, 3, 5, 14, 21, 28…）。移行の突合キーなので必ず保持する
  master_no     int  not null unique,
  title         text not null,                  -- 作業名（作業タイトル）
  title_note    text,                           -- 作業の補足（連絡票で作業名の下に青文字で出る）
  content       text,                           -- 作業内容（予定詳細の「補足」）
  notice        text,                           -- 注意事項（告知）。連絡票の「(4) 留意事項」
  place         text,                           -- 作業場所。連絡票の「(2) 場所」
  enter_room    boolean not null default false, -- 入室作業（日程表の「入室あり*」に ✓）
  notify        boolean not null default false, -- 報知対象（掲示・メールに載せるか。3-4）
  jurisdiction  text,                           -- 管轄（'栄和' | '小泉産業'）
  vendor_code   text,                           -- 担当会社コード（K-004 等）
  vendor_name   text,                           -- 担当会社名（セコム / 明和ビル管理 …）
  worker_name   text,                           -- 実施業者名（担当会社の下請け等）
  prep_note     text,                           -- 管理側作業・準備（一覧の青■ラベル）
  plan_start    time,                           -- 既定の予定開始時刻
  plan_end      time,                           -- 既定の予定終了時刻
  -- 定例実施月。{1,3,5,7,9,11}。空配列＝自動作成の対象外（随時作業）
  months        int[] not null default '{}',
  day_pattern   text,                           -- 実施日パターン（'月半ば' 等。フリーテキスト）
  -- 不規則周期のメモ（'2019,2022,2025,2028' / '3年に1回（2025年〜）'）。機械判定はしない（1章）
  cycle_pattern text,
  memo          text,                           -- 管理メモ／注意事項（社内専用）
  remark        text,                           -- 備考
  sort_order    int  not null default 999,      -- 表示順（10, 20, 30…。再採番機能あり）
  disabled      boolean not null default false, -- 無効（選択肢に出さない。過去の予定は残す）
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
create index if not exists bilmen_masters_order_idx
  on bilmen_masters (disabled, sort_order, master_no);

-- ---------- メンテナンス予定・実績（2-1・2-2） ----------
create table if not exists bilmen_schedules (
  id            uuid primary key default gen_random_uuid(),
  -- 作業ID（W260901-27）。カレンダー説明欄にも出す識別子。**移行時は現行の値をそのまま継承し、
  -- 新規分は現行どおり手入力**（13-5 回答済み。自動採番はしない）。
  -- ★nullable にしてある: 予定の自動作成（5-3）は複数行を一括生成するため、その時点では
  --   まだ人が作業IDを入力していない。unique は NULL を重複と見なさないので
  --   「未入力の行は複数あってよい／入力された値は一意」をこの1本で表現できる
  work_no       text unique,
  master_id     uuid references bilmen_masters(id) on delete set null,
  -- 対象月 'YYYY-MM'。予定日が未定でも「その月の予定」として一覧・帳票に並べるため必須
  target_month  text not null,
  plan_date     date,                            -- 予定日付（自動作成直後は null＝日付未定）
  plan_start    time,
  plan_end      time,

  -- ↓ マスタからの複写（3-2）。以後マスタを直しても過去の予定は変わらない
  title         text not null,
  title_note    text,
  content       text,
  notice        text,
  place         text,
  enter_room    boolean not null default false,
  notify        boolean not null default false,
  jurisdiction  text,
  vendor_code   text,
  vendor_name   text,
  worker_name   text,
  prep_note     text,
  remark        text,

  memo          text,                            -- 管理メモ（'9/3から9/4に変更されました'）

  -- ↓ 実績
  actual_date   date,
  actual_start  time,
  actual_end    time,
  actual_note   text,                            -- 作業実績報告事項
  report_confirmed_on date,                      -- 報告書確認日付
  canceled      boolean not null default false,  -- 中止
  cancel_reason text,

  -- ↓ Google カレンダー連携（7-2）
  google_event_id  text,
  google_synced_at timestamptz,

  sort_order    int  not null default 999,       -- 同一日内の並び
  created_by    text,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
create index if not exists bilmen_schedules_month_idx
  on bilmen_schedules (target_month desc, plan_date, sort_order);
create index if not exists bilmen_schedules_date_idx
  on bilmen_schedules (plan_date);

-- ---------- 実施報告書ファイル（2-2 右下） ----------
create table if not exists bilmen_report_files (
  id          uuid primary key default gen_random_uuid(),
  schedule_id uuid not null references bilmen_schedules(id) on delete cascade,
  storage_key text not null unique,              -- Supabase Storage の非公開バケット
  filename    text not null,
  mime        text,
  size        int,
  sort_order  int not null default 0,
  created_at  timestamptz not null default now()
);

-- ---------- 今月の注釈（2-1 の月見出しボタン） ----------
create table if not exists bilmen_monthly_notes (
  target_month text primary key,                 -- 'YYYY-MM'
  note         text,                             -- 掲示物・メール本文に差し込む月固有の但し書き
  updated_by   text,
  updated_at   timestamptz not null default now()
);

-- ---------- 案内メールの宛先（2-8 BCCタブ） ----------
create table if not exists bilmen_mail_recipients (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,                      -- テナント名
  email      text not null,
  note       text,                               -- 運用メモ（'エラー返信があるが到達' 等）
  disabled   boolean not null default false,     -- 一時的に送らない
  sort_order int  not null default 999,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create unique index if not exists bilmen_mail_recipients_email_idx
  on bilmen_mail_recipients (lower(email));

-- ---------- 案内メールの文面（2-8 雛形定義タブ） ----------
create table if not exists bilmen_mail_templates (
  id          uuid primary key default gen_random_uuid(),
  code        text not null unique,              -- 'MAINT'
  name        text not null,                     -- 'ビルメンテナンスのお知らせ'
  description text,                              -- 用途と補足説明
  subject     text not null,                     -- 件名雛形（'…（%対象年月%）'）
  body        text not null,                     -- 本文雛形
  is_default  boolean not null default false,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

-- ---------- 送信ログ ----------
create table if not exists bilmen_mail_logs (
  id           uuid primary key default gen_random_uuid(),
  target_month text not null,
  mode         text not null,                    -- 'draft'（下書き作成） | 'send'（直接送信）
  subject      text,
  body         text,
  recipients   jsonb,                            -- 送信時点の宛先スナップショット
  attachment   text,                             -- 添付PDFのファイル名
  gmail_id     text,                             -- 下書きID or メッセージID
  ok           boolean not null default true,
  error        text,
  sent_by      text,
  sent_at      timestamptz not null default now()
);
```

### 5-2. 予定詳細モーダル

現行（2-2）の2カラム構成を踏襲。PC は左＝予定・右＝実績、**iPhone 幅では1カラムに縦積み**
（予定 → 実績 → Google の順）。

- 上部に**作業ID（`W260901-27`）の入力欄**と、マスタの実施月列挙（読み取り専用）を表示
  - 作業IDは**手入力**（自動採番しない。13-5）。**空欄のまま保存でき**、後から埋められる
  - 保存時に**重複チェック**（前後空白・大文字小文字を正規化して比較）。衝突したらエラー表示
- 「予定通り ➡」ボタンで実績へコピー
- 「Google カレンダーに反映」ボタン。反映済みなら `google_synced_at` と「再反映」表示
- 中止☑ にすると中止理由が必須になり、**カレンダー登録済みならイベントを削除**する（7-2）
- 実施報告書ファイルは既存の添付UI（`AttachmentPreview.jsx`）を流用

### 5-3. 予定の自動作成モーダル

1. 対象年月を選ぶ（既定＝**翌月**。現行の運用サイクルが「翌月分を当月中に確定」のため）
2. `months` に対象月を含む**有効なマスタ**を一覧表示し、チェックで取捨選択（既定＝全選択）
   - 既に同じ月・同じマスタの予定がある場合は**チェック不可＋「作成済み」表示**（二重作成の防止）
   - 「パターン」（不規則周期のメモ）があるマスタは行に**注意アイコン＋パターン文字列**を出し、
     人が「今年は対象か」を判断できるようにする（1章のとおり自動判定はしない）
3. 「作成」で予定を一括生成。**予定日付は null（日付未定）**、時刻はマスタの既定値を入れる。
   **作業ID（`work_no`）も空のまま**にする（自動採番しない。13-5）
4. 作成後は一覧の「日付未定」グループに並ぶので、そこに**日付と作業IDを入れて確定**していく

> 一覧の「日付未定」グループは、日付だけでなく**作業IDが未入力の行も拾う**ようにする
> （どちらも「確定作業が残っている」ことを示すため）。掲示・メール・カレンダーの各出力時には、
> 未入力の行が残っていれば件数を添えて警告する（→ 13-6）。

### 5-4. 今月の注釈モーダル

対象月のテキストを1つ編集するだけの小さなモーダル。掲示PDF・メール本文の `%今月の注釈%` に入る。

### 5-6. メール設定 `/bilmen/mail`

タブ2つに簡素化する（現行の TO/CC/表示確認/アドレス展開確認は使っていないため落とす）:

## 7. 外部連携

### 7-1. 【最重要】Google OAuth スコープの拡張が前提

**現状**（`worker/lib/gmail.js` / `worker/lib/calendar.js` の実装から確認）:

| 用途 | 現在のスコープ | 実装 |
|---|---|---|
| メール取得（パイプライン） | `gmail.readonly` | 読み取り専用 |
| カレンダー参照 | `calendar.readonly` | 読み取り専用 |

**13-10 の回答により、(4) カレンダー自動登録は正式に実施することが確定した**ため、
`calendar.events` の追加は**必須**である。一方 (3) メール送信は 3-5 の方式B（`mailto:`）を選べば
スコープ不要で実装できるため、`gmail.compose` の追加は**任意（方式Aを使う場合のみ必要）**。

| 用途 | 必要なスコープ | 必須か |
|---|---|---|
| カレンダー自動登録（(4)） | `calendar.events` | **必須**（13-10 で実施が確定） |
| 案内メール 方式A（Gmail下書き） | `gmail.compose` | 任意（方式Bなら不要） |

次の対応が要る:

1. Google Cloud Console の OAuth クライアントで、同意を取り直して**新しいリフレッシュトークンを発行**する
2. 発行時に要求するスコープは**現行分を含めた和集合**にする（既存パイプラインを壊さないため）:
   - `https://www.googleapis.com/auth/gmail.readonly`（既存・維持）
   - `https://www.googleapis.com/auth/calendar.events`（**追加・必須**。予定の作成・更新・削除）
   - `https://www.googleapis.com/auth/gmail.compose`（**追加・任意**。下書き作成と送信の両方を含む）
   - ※ `calendar.readonly` は `calendar.events` に包含されるため個別指定は不要
3. Worker シークレット `GMAIL_REFRESH_TOKEN` を差し替える（`wrangler secret put` または CI 経由）

> **`gmail.send` ではなく `gmail.compose` を要求する理由**: 3-5 のとおり下書き作成で運用するため。
> `gmail.compose` は下書き作成と送信の両方を含むので、将来直接送信に切り替える場合も
> **再同意（トークン再発行）をしなくて済む**。

> **`calendar.events` だけなら審査リスクが低い**: `gmail.*` は Google の「制限付きスコープ」だが、
> `calendar.events` は「機密スコープ」で一段緩い。**カレンダーだけ先に通す**という進め方もできるため、
> `gmail.compose` の追加で審査を求められた場合は、メールを方式B（`mailto:`）で運用しつつ
> カレンダーだけ自動化する、という着地が可能（→ 14章のリスク表）。

> **リスク**: `gmail.*` は Google の「制限付きスコープ」であり、OAuth アプリの公開状態によっては
> 追加時に審査・再確認を求められる可能性がある。既に `gmail.readonly`（同じく制限付き）で
> 運用できているため通る見込みだが、**着手前に実際にトークンを取り直せることを確認したい**（→ 13-1）。

### 7-2. Google カレンダー反映

- 対象カレンダー: **`栄和共通`**。既存の `resolveCalendar(accessToken, name)`（`worker/lib/calendar.js`）で
  カレンダー名から ID を引ける。カレンダー名は `settings` に持たせて変更可能にする
- イベント内容:

  | 項目 | 値 |
  |---|---|
  | summary | 作業名（`title`） |
  | start / end | 予定日付＋予定時刻（`Asia/Tokyo`）。時刻未設定なら終日イベント |
  | description | `(by 担当会社名)` ＋ 改行 ＋ `--- created by 栄和業務管理システム:W260901-27 at YYYY/MM/DD HH:mm:ss`<br>※ 作業IDは手入力のため未入力がありうる（13-5）。**未入力ならID部分を省いて出力**し、画面側で警告する |
  | location | 作業場所（`place`） |
  | reminders | 10分前（現行と同じ） |

- **冪等性**: `google_event_id` を保持し、**あれば PATCH、なければ POST**。再反映で重複を作らない
- **中止・削除時**: `google_event_id` があればイベントを DELETE してから列を null に戻す
- 月まとめ反映は、対象月の**予定日付が入っている**行だけを対象にする（日付未定はスキップ）
- 失敗した行はスキップして続行し、結果を「成功 n件 / 失敗 m件（理由）」で返す

> 3-3 のとおり、FileMaker と並行運用する間はフッタ文言を分けて出所を判別できるようにする。

#### 現行の連携方式からの移行（2026-09-02 回答で判明）

現行は **FileMaker → Claris Connect → Google カレンダー**という経路で登録・修正している。
本システムは Claris Connect を介さず、**Worker から Calendar API を直接叩く**（中間サービスが減り、
Claris Connect の契約・フロー保守が不要になる）。

移行時に必ず整理すること:

1. **二重登録の防止**: 本システムから登録を始める月からは、**Claris Connect 側の該当フローを停止**する。
   停止前に本システム側を有効にすると、同じ作業のイベントが2つ並ぶ
2. **切り替え月の既存イベントの扱い**: 切り替え月に Claris Connect が既に作ったイベントがある場合、
   本システムはその存在を知らない（`google_event_id` が空）ため、反映すると重複する。
   運用手順を次のどちらかに決める（→ 13-15 で確認）:
   - (a) 切り替え月は Claris Connect 側で作ったイベントを**手動で削除**してから本システムで反映する
   - (b) 本システムからの登録は**翌月分から**開始し、切り替え月は現行のまま流す（**推奨**。事故が無い）
3. **過去イベントの引き取りはしない**: 移行前に作られたイベントの `google_event_id` は取り込まない。
   過去の予定を本システムから編集してもカレンダーには反映されない（実務上、過去分の修正は発生しない）

### 7-3. 案内メールの送信

**フロー**（3-5 の「作って確認してから出す」。②までは両方式で共通）:


  **`settings` に持たせる**（テーブル列ではなくシステム設定）。改称時に1か所直せば
  日程表・連絡票・メール本文のすべてに効く
- 日報機能には `building`（BKB／小泉本社）の概念があるが、**ビルメンは BKB のみ**で独立している。
  将来2棟目が出た場合は `building` 列の追加とデータの振り分けが必要になる（現時点では作らない）

### 13-5. 作業ID（`W260901-27`）の体系 ✅**【2026-09-02 回答済み】**

> **回答**: 作業IDは**類似の作業を隣同士に揃えるくらいの緩いルール**。
> データ移行に際しては**現在のIDを継承する**。

**確定事項**:

- **移行時は FileMaker の作業IDをそのまま `work_no` に入れる**（採番し直さない）。
  カレンダーの説明欄にも出ている識別子なので、過去の照合可能性を保つ
- 同様に**作業マスタIDも `master_no` にそのまま継承する**（4-1 のとおり `not null unique`）
- 厳密な計算式は無い（緩いルール）ため、**移行データに対して体系の妥当性チェックはしない**。
  重複だけを検査する（→ 9章）

**新規作成分の採番** ✅**【2026-09-02 追加回答】**

> **回答**: 新規作成分も**現行どおり手入力**とし、**重複チェックのみ**でよい。

- **システムは作業IDを自動採番しない**（当初案の自動採番は取りやめ）
- 予定詳細モーダルで人が入力する。**空欄のまま保存できる**（後から埋める運用を許す）
- 保存時に**重複だけを検査**し、既存の作業IDと衝突したらエラーにする
  （大文字小文字・前後空白を正規化して比較する）

**この回答による設計変更（重要）**:

`work_no` を **`not null` から nullable に変更する**（4-1 のスキーマを修正済み）。

理由は、予定の自動作成（5-3）が**複数行を一括生成する**機能であり、その時点では
作業IDを人が入力していないため。`not null` のままだと一括生成そのものが成立しない。

- PostgreSQL の `unique` 制約は **NULL を重複と見なさない**ため、
  「作業ID未入力の予定が複数あってよい／入力された値は一意」という要件をそのまま表現できる
- 作業IDは Google カレンダーの説明欄にも出る（7-2）ため、**カレンダー反映時に未入力なら警告**を出す
  （反映自体は可能にし、説明欄の該当部分を省く）

## 14. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| **OAuth スコープ拡張ができない** | Phase 3（カレンダー）・4'（PDF自動添付）が実施不能 | Phase 1・2・4 はスコープ不要で完遂できる（12章）。メールは方式B（`mailto:`＋手動添付＝現行と同じ手数）で運用継続。カレンダーのみ当面 Claris Connect を残す |
| **`gmail.compose` だけ審査で止まる** | PDFの自動添付ができない | `calendar.events`（機密スコープ）と `gmail.compose`（制限付きスコープ）は**別々に扱える**。カレンダーだけ先に通し、メールは方式Bで運用する着地が可能（7-1） |
| **リフレッシュトークン差し替えでパイプラインが停止** | メール自動取得が止まる（業務影響大） | 新トークンは**現行スコープを含む和集合**で取得。差し替え直後に `/logs`（操作ログ）で取得成功を確認し、失敗なら即座に旧トークンへ戻す |
| **案内メールの誤送信** | 社外テナントへの影響 | システムは直接送信しない（3-5）。送信前プレビュー＋確認ダイアログ＋送信ログ＋二重送信警告 |
| **方式Bで PDF の添付を忘れて送信** | 添付なしのメールがテナントへ届く | メール作成画面に「PDFを添付してから送信してください」を明示（7-3）。本文にも添付前提の文言が入るため受信側でも気付ける。**方式Aへ移行すれば構造的に解消する** |
| **カレンダーの二重登録（Claris Connect との併走）** | 同じ予定が2つ並ぶ | `google_event_id` による冪等更新（7-2）。切り替えは**翌月分から**開始し、その前に Claris Connect のフローを停止する（13-15） |
| **掲示PDFの体裁が現行と違う** | 掲示物として使えない | 実物のPDFを1部いただき、**同じ月のデータで並べて比較**してから確定する |
| **不規則周期（3年に1回等）の作業を作り忘れる** | 法定検査の失念 | 自動作成モーダルでパターン付きマスタに注意アイコンを出す（5-3）。自動判定はしない |
| **移行データの例外行** | 取込失敗・不整合 | 9章の機械検証を全件に対して先に流し、例外を洗い出してから投入（備品管理で実際に9件の例外を検出した実績あり） |

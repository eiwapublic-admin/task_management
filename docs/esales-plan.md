## 1. 目的と範囲

### 目的

FileMaker で運用中の販売管理アプリ **eSales2**（画面上の表記は「販売管理システム eSales 3」）を、
タスク管理システムと同じ基盤（React / Cloudflare Workers / Supabase）の Web アプリへ移行する。

- **業務機能は現行踏襲**（見積 → 受注 → 売上 → 請求 → 入金、発注 → 仕入 → 支払、定期作業の予定展開、帳票、経理連携）
- **UI は刷新**（モダン・視認性・操作効率を重視。Mac / Windows / iPhone / iPad のレスポンシブ）
- **基盤機能は新規に作らない**（ログイン・帳票PDF・メール・写真・バックアップ・ログは既存実装を踏襲）
- 利用者は既存のタスク管理システムと重複するため、**ログインを共通化**する

### 範囲に含むもの

| 区分 | 内容 |
|---|---|
| 売上系 | 見積／受注雛形／受注予定／受注／売上／入金 の各伝票、伝票の複写・進行、入金差額の値引伝票 |
| 仕入系 | 発注／仕入／支払 の各伝票、売上系から発注・仕入を一括生成 |
| 定期作業 | 受注雛形の予定展開（展開パターン）、受注予定 → 受注の発行確認、日程調整、作業予定・予定案内 |
| 締め処理 | 請求締め（締日 15・20・31）、請求書4種、確認・承認、得意先元帳、仕入先元帳（元帳締め） |
| 作業管理 | 作業カレンダー、作業実績、報告書（写真つき）、スマホでの撮影・登録 |
| 帳票 | 12章の一覧（見積書・注文請書・作業指示書・納品書・請求書・領収書・発注書・元帳ほか）、出力帳票一覧、メール送付 |
| 分析・連携 | 月別／得意先別の売上推移、仕入実績、得意先別伝票遷移、経理ソフト向け CSV |
| マスタ・管理 | 得意先（納品先・請求単位・担当者）、仕入先、商品、担当者、会社情報、消費税率、設定値、処理ログ |
| データ移行 | マスタ・全伝票・締め結果・元帳・帳票PDF・関連書類・作業写真 |

### 範囲に含めないもの（13章で確認）

現行にあるが**データが0件、または FileMaker 固有**のため、初期の範囲から外す候補。

| 機能 | 理由 |
|---|---|
| 経費申請・経費明細 | テーブルが 0 件（未使用） |
| 支払締め（支払管理） | テーブルが 0 件。実運用は「仕入先元帳の元帳締め」で回っている |
| はがき印刷（年賀状・お歳暮） | FileMaker のレイアウト印刷前提。必要なら宛名 CSV 出力で代替 |
| ライセンス設定・規約、フリー電卓、旧データの削除 | FileMaker 配布用の仕組み／OS の機能で代替可 |
| メンテナンス記録・バージョン情報 | GitHub のコミット履歴と `docs/HANDOFF.md` で代替（過去分は参照用に CSV 保管） |
| 担当者マスタの給与項目（月給・手当・社保など） | 販売管理の範囲外。**機微情報のため移行しない**ことを推奨 |

## 2. 結論（先に要点）

1. **内部は既存アプリに統合し、入口は別アプリにする**（同じリポジトリ・同じ Supabase・同じログイン ID。
   URL・ホーム画面・PWA は販売管理専用）。理由は 5-1・5-1b。
2. **追加の月額費用は 0 円で始められる。** DB は現在 27MB／上限 500MB で、販売データ（推定 150〜250MB）が入る。
   ただし **ファイル保管（作業写真 約2.3万枚）は Supabase 無料枠 1GB に収まらない**ため、保管先の判断が要る（5-4・13章①）。
3. **伝票は現行と同じ「1テーブル＋伝票区分＋複写で進行」の構造を保つ。** 構造を変えないことで、
   42,674 件の売上系伝票を機械的に移行でき、現行との突合テストが成り立つ。
4. **金額・消費税の計算は 1 か所（共有モジュール）に集約**し、移行済みの過去データで
   「FileMaker の請求金額と 1 円単位で一致するか」を自動検証する（11-3）。販売管理で最も壊せない部分。
5. **作る順番は「マスタ → 売上系伝票 → 帳票 → 仕入系 → 予定展開 → 請求締め → 元帳・分析 → 作業管理」**。
   各フェーズ単位でリリースし、**FileMaker と並行運用**しながら進める。全 10 フェーズ・目安 22〜30 セッション（10章）。

### 3-3. 伝票の流れ（業務の骨格）

```
【売上系】                                              【仕入系】
 見積 ──複写──▶ 受注 ──進行──▶ 売上 ──請求締め──▶ 請求書      発注 ──進行──▶ 仕入 ──元帳締め──▶ 仕入先元帳
   │              ▲              │                  │           ▲             │
   └─複写─▶ 受注雛形            │                入金 ◀───────┘           支払
              │ 予定展開（月次）   │                  │
              ▼                  └── 発注・仕入を一括生成 ──────────────────▶（仕入系へ）
           受注予定 ──発行確認──▶ 受注                └─ 入金差額（振込手数料）→ 値引の売上伝票を自動生成
```

- **伝票は「複写して次の区分へ進める」方式**。各伝票は「コピー元」「コピー先」を持ち、見積 No.・受注 No.・売上 No. が
  帳票の右肩に並ぶ（例: 納品書に「見積 No.23585／受注 No.44799／売上 No.46368」）
- 伝票番号は区分ごとの連番（2026-11 時点: 見積 2.3万台／受注 4.4万台／売上 4.6万台／入金 2.7万台／
  発注・仕入 5.9万台／支払 5.2万台／請求番号 20万台）。**移行後も続き番号で採番**する
- 1 伝票に **得意先・得意先担当者・納品先・請求単位・営業担当・作業担当（社員 or 協力会社）・サービス区分** が付く
- 明細は「処理区分（売上・値引など）／商品／入数／数量・単位／販売単価・仕入単価／消費税区分・課税方法／備考／仕入先」。
  **販売と仕入を同じ明細行に持ち、伝票ごとに粗利額・粗利率を出している**

### 3-4. 定期作業（受注雛形 → 予定展開）

日常清掃・定期清掃・レンタルなどの繰り返し受注を、雛形から毎月まとめて生成する仕組み。現行の中核機能の一つ。

- 受注雛形に **対象月（1〜12月のチェック）** と **展開パターン** を設定する。パターンは曜日マスタ（78 件）で定義され、
  スクリプトは 4 種: **特定日**（指定月の n 日・末日）／**毎 n 曜日**／**第 n・m 曜日**／**m 週ごとの n 曜日**（隔週は開始日指定）
- 「雛形一覧と予定発行」画面で期間を指定 → **受注予定伝票を一括発行** → 「予定から受注へ」画面で 1 件ずつ受注へ進める
- **日程都度調整**（協力会社／得意先のそれぞれに「調整要」「調整済日」「メモ」）を持ち、未調整は赤く警告される
- 「作業予定・予定案内」画面で、**作業担当（協力会社）別／得意先別に月間の作業予定表 PDF を作り、メールに添付**する

### 3-5. 消費税・インボイス

設定の組み合わせが多く、移行で最も注意が要る。

| 設定 | 値 | 持ち方 |
|---|---|---|
| 消費税区分 | 1 標準（最新税率）／2 軽減／9 非課税 | 明細ごと。税率は「適用開始日」つきの履歴（1997/5% → 2014/8% → 2019/10%） |
| 課税方法 | 外税／内税／非課税 | 明細ごと（既定は 会社 → 得意先 → 商品 の順で上書き） |
| 消費税集計方法 | 伝票単位計算 など | 会社既定＋得意先／仕入先ごとの個別指定 |
| 端数処理 | 切り捨て など 3 種 | 同上 |
| 消費税転嫁区分 | 伝票毎課税／**請求毎課税（原則）** | 得意先・仕入先ごと。請求単位ごとの個別指定もあり |

- 請求書は **税率別の内訳（対象金額・税額）と登録番号** を表示（インボイス対応済み）
- 請求毎課税の場合、**納品先別請求書は納品先単位、請求単位別請求書は請求単位で税を再計算**する
  （帳票に「＊納品先ごとの合計金額で消費税計算しています」と注記）。伝票単位の税額の単純合計とは一致しない

### 3-6. 請求締め

- 締年月と対象締め日（15／20／31）を選び **「請求締処理」** を実行 → 得意先ごとに
  前月残高・入金額・繰越金額・販売金額（税込）・当月残高 を確定し、請求番号を採番
- **請求書種類**は得意先ごとに設定: 「1 得意先別」「2 得意先＋納品場所別」。さらに請求単位マスタ（25 件）がある得意先は請求単位別
- 得意先ごとに **確認1・確認2・承認** のチェック（担当者印・社印が画面と帳票に出る）、PDF 保存・印刷・**メール送付**
- 「請求しない伝票」フラグ（包括契約の内訳など）、入金伝票からの **値引伝票の自動発行**（振込手数料分）

### 3-7. 権限

アクセス権セット: システム管理者／マスタ管理者／承認者／標準業務ユーザ／作業報告ユーザ／**仕入先ユーザ**／**得意先ユーザ**／閲覧ユーザ。
現在のアカウントは 15 件（うち得意先ユーザ 3・仕入先ユーザ 1・作業報告ユーザ 4）。
仕入先ユーザは自社宛の発注だけ、得意先ユーザは自社の受注だけが見える専用ポータルを持つ。

### 3-8. スマホ（iPhone）用画面

メニュー／作業予定一覧・月間／作業管理詳細（**カメラ撮影・写真ライブラリから追加**）／作業場所の地図／
見積伝票の一覧・詳細／得意先・仕入先マスタ詳細。現場での **作業報告と写真登録** が主用途。

### 3-9. 現行の課題（刷新で解消したい点）

| 現行 | 課題 |
|---|---|
| 1 伝票ごとに別ウインドウが開く | ウインドウが増え、「他のウインドウを全て閉じる」ボタンが必要になっている |
| 入力欄が小さく密集（コード欄＋「＊」検索ボタン） | 視認性が低い。コードを覚えていないと速く打てない |
| 伝票の進行状況がタブ「コピー元・先」を開かないと分からない | 見積〜入金のどこまで進んだか一目で分からない |
| iPhone 用に別レイアウトを作り分け | 機能が限られ、iPad／Windows は PC 用画面を縮小して使うしかない |
| メールは OS のメールソフトを起動 | 端末依存。送信履歴がアプリに残らない |
| 締め処理・予定展開をサーバースクリプトで実行 | 処理中は白紙画面で待つ。途中失敗時の状態が分かりにくい |

## 5. 全体方針

### 5-1. 既存アプリに「販売」セクションとして統合する（推奨）

| | A. 既存アプリに統合（**推奨**） | B. 別アプリとして新設 |
|---|---|---|
| ログイン | 共通（既存の JWT・`users`）。**追加作業なし** | 認証を二重に持つか、共通化の仕組みが別途必要 |
| 基盤 | PDF・メール・写真・Push・ログ・バックアップを**そのまま使える** | コードを複製 → 以後 2 か所を保守 |
| 費用 | 追加 0 円（Worker・Supabase とも既存の無料枠内） | Supabase 無料枠は 2 プロジェクトまで。Worker は追加可 |
| 連携 | 日報・ビルメン・連絡先・カレンダーと**同じ DB でつながる** | API 連携が必要 |
| 懸念 | 画面数が増える → **遅延読み込み**で初期表示を守る（下記）。障害の影響範囲が広がる | 分離による安全性は高い |

A を推奨する。懸念への手当て:

- **フロントは販売セクションを遅延読み込み**（`React.lazy`）にし、タスク・日報だけ使う利用者の初期表示を重くしない
- **コードは `src/pages/sales/`・`src/components/sales/`・`worker/lib/sales/` に閉じる**。既存ファイルへの変更は
  ルーティング・ヘッダ・権限判定に限る（備品・ビルメンを足したときと同じ流儀）
- **テーブルは `sales_` 接頭辞**で統一する。将来分離したくなったら、接頭辞単位で切り出せる
- DB の負荷・容量は 5-3 のとおり無料枠内

### 5-1b. 入口を別アプリにする方法（2026-11-14 決定を受けて追加）

依頼元の要望: 内部は統合してよいが、**アプリの入口（ホーム画面）は別**にし、**PWA も別アプリとして Dock に追加**したい。

| | 方式X: 別 URL（別 Worker）で配信（**推奨**） | 方式Y: 同じ URL の `/sales/` 配下 |
|---|---|---|
| 構成 | 同じリポジトリから **2 つ目の Worker `esales`** をデプロイ（例: `esales.eiwa-public.workers.dev`）。DB と `worker/lib` の共通コードは共有 | 既存 Worker の中に `/sales/` を足し、専用の manifest（`scope: /sales/`）を返す |
| 別アプリとしての追加 | **確実**。URL が違うので、Mac の Dock・Windows・iPhone・iPad のどれでも独立したアプリになる | 同じ URL に 2 つの PWA を入れる形になり、Chrome／Edge では範囲が重なって**片方しか入らない・リンクが別アプリで開く**おそれがある |
| ログイン | ID・パスワードは共通。**アプリごとに 1 回ずつログイン**が必要（保存場所が URL ごとに分かれるため） | 1 回のログインで両方使える |
| 既存への影響 | 既存 Worker・既存 PWA に手を入れない。販売側の不具合がタスク管理に波及しない | 既存の Service Worker・manifest・ルーティングを変更する |
| 費用 | 0 円（Workers 無料枠は Worker 数ではなくリクエスト数で数える。1 日 10 万回はアカウント合計） | 0 円 |

**方式X を推奨**する。「別アプリとして Dock に追加」を端末によらず満たせるのは X だけで、既存アプリを触らずに済む。
引き換えに 2 回ログインが要るが、ログインは 30 日保持されるため日常の負担は小さい。

方式X での作り:

- フロント: Vite の入口を 2 つにする（既存 `index.html` と、販売用 `sales.html` → `src/sales/main.jsx`）。
  **UI トークン・共通部品（`src/styles/ui.css`・`Combobox.jsx` など）と `src/lib` は共有**し、画面は `src/sales/` に置く
- Worker: 販売用の入口 `worker/sales.js`（`/api/login`・`/api/sales/*` と販売用アセットを返す）。認証・Supabase・Gmail・Storage などは既存 `worker/lib` を import
- 設定: `wrangler.sales.jsonc`（アセットは `dist-sales`、R2 バケットのバインド、同じシークレット）。`deploy.yml` に 2 つ目のデプロイ手順を追加
- PWA: 販売用の `manifest`（名前 `eSales`、専用アイコン、`start_url: /`）と Service Worker
- **Phase 1 の最初に、空のホーム画面だけの状態で 4 端末（Mac・Windows・iPhone・iPad）へ追加できるかを実機確認する**。
  ここで問題が出た場合のみ方式Y を再検討する
- HANDOFF.md に「アカウントに残す Worker は 1 つだけ」とあるのは不要 Worker を整理した際の方針。販売用 Worker を足すことを追記する

### 5-3. 無料枠の見通し

2026-11-14 時点の実測と、移行後の見積り。

| 資源 | 無料枠 | 現在 | 販売管理の追加（推定） | 判定 |
|---|---|---|---|---|

### 5-4. ファイル保管先（要判断・13章①）

現行は FileMaker 内に **作業写真 23,473 枚・関連書類 1,554 件・出力帳票 PDF 2,961 件** を保持している。
実サイズは FileMaker 側で確認が必要（14章 手順3）だが、写真は 1 枚 150〜300KB として 3〜7GB になり、
Supabase Storage の無料枠（1GB。既存の日報写真と共用）には入らない。

| 案 | 内容 | 費用 | 評価 |
|---|---|---|---|
| **a. Cloudflare R2**（推奨） | 写真・帳票・関連書類を R2 に置く。Worker から直接読み書きできる | **10GB／月まで無料**。超過分は約 0.015 USD／GB・月。**利用開始に支払い方法（クレジットカード）の登録が必要** | 全件移行できる。10GB を超えない限り 0 円 |
| b. Supabase Storage のみ | 帳票 PDF・関連書類＋**直近 1〜2 年分の写真だけ**移行。古い写真は FileMaker のバックアップで保管 | 0 円（1GB を超えると書き込み不可になる。自動課金はされない） | 追加契約なし。ただし数年で上限に達する |
| c. Supabase Pro へ変更 | Storage 100GB・DB 8GB | **月 25 USD** | 最も単純だが恒常的に課金 |

- **a に決定（2026-11-14）**。課金の可能性があるのは「10GB 超過時」のみ。Cloudflare ダッシュボードで使用量を確認でき、
  超過前に古い写真を整理する運用にすれば 0 円を保てる
- どの案でも、**新規に撮る写真は端末側で長辺 1,600px 程度へ縮小**してから保存する（既存の日報と同じ）
- **新システムで作る帳票 PDF は画像方式のため 1 ページ 100〜300KB** になる（FileMaker の PDF は 60KB 程度）。
  請求書を毎月全件保存すると年 0.3〜0.5GB 増える見込み。対策は 6-5

### 5-5. バックアップの容量対策

既存の日次バックアップは `data.sql` を別リポジトリへコミットしている。**GitHub は 1 ファイル 100MB が上限**のため、
販売データ（数百 MB）を入れると push が失敗する。Phase 2（伝票データ移行）の前に、次のどちらかへ変更する。

- ダンプを **gzip 圧縮＋テーブル群ごとに分割**してコミットする（販売系は `sales_data.sql.gz` として分離）
- 変更の少ない過去年度の伝票を別ファイルにし、日次では当年度分だけ更新する

あわせて、**ファイル本体（R2 または Storage）のバックアップ**方針を決める（現状、Storage のファイル本体は
workflow で取得している。R2 に移す場合は取得先を追加する）。

## 6. データモデル

### 6-1. 設計の原則

1. **伝票の構造は現行を保つ**（売上系 1 テーブル・仕入系 1 テーブル。伝票区分で区別。複写で進行）
2. **計算・集計フィールドは持たない。** 現行 281 フィールドの大半は計算・集計・帳票用・画面制御用（`g_`・`c_`・`flg_`）。
   新 DB には**入力値と、確定させるべき金額だけ**を列として持つ（売上系伝票は 60 列前後になる見込み）
3. **確定した数字は保存する。** 伝票の合計・税額、請求締めの結果は、後から税率やマスタが変わっても動かないよう保存する
4. **コードは現行の値をそのまま持つ**（得意先コード `00089`、納品先コード `AO002` など）。帳票・経理連携・利用者の記憶と一致させる。
   内部の主キーは別に持つ（uuid）
5. **伝票番号は Postgres のシーケンス**で採番（区分ごと）。移行時に現行の最大値＋1 へ合わせる
6. **同時編集は楽観ロック**（`updated_at` の一致確認）。FileMaker のレコードロックの代わり

### 6-2. 主なテーブル

| テーブル | 元 | 内容 |
|---|---|---|
| `sales_company` | 会社基本情報 | 自社情報・振込先・登録番号・角印・ロゴ・既定の税設定 |

| **`sales_slip_lines`** | 売上系明細 | 商品・数量・単価・仕入単価・税・備考・仕入先／入金明細（現金・振込・手数料・調整） |

| `sales_closings` | 締め処理 | 締め実行の単位（実行番号・締年月・締め日・実行者） |
| `sales_invoices` ／ `sales_invoice_units` ／ `sales_invoice_lines` | 請求管理・請求単位管理・請求管理_明細 | 請求番号、前月残高・入金・繰越・販売額・税率別内訳、確認・承認 |

- 推移分析（売上推移分析テーブル）は**ビュー／集計クエリ**に置き換え、テーブルとしては持たない
- 祝日・処理ログ・ユーザは**既存テーブルを使う**

### 6-3. 金額・消費税の計算

- 計算は **`src/lib/sales/calc.js`（共有モジュール）に一本化**し、画面（入力中の即時表示）と Worker（保存時の再計算・検証）の
  両方から同じコードを呼ぶ。画面で見た金額と保存される金額が食い違わない
- 対象: 明細金額、外税・内税の分離、端数処理、伝票単位／請求単位／納品先単位の税額、税率別内訳、粗利
- **仕様は FileMaker の計算式とスクリプトを Phase 0 で読み解いて文書化**する（デザインレポートに全計算式が載っている）。
  推測で実装しない
- 保存時は Worker が再計算した値を正とし、画面から送られた合計は信用しない

### 6-4. 複数テーブルにまたがる処理

伝票の保存（ヘッダ＋明細）、複写・進行、予定展開、請求締め、元帳締めは、**途中で失敗すると不整合が残る**処理。
これらは **Postgres の関数（RPC）として実装し、1 トランザクションで実行**する。
Worker の CPU 制限（10ms／回）にも掛からず、現行の「サーバー実行」に相当する。

- 請求締めは **「計算して結果を見せる（下書き）」→「確定」の 2 段階**にする。確定前なら何度でもやり直せる
- 締め済みの月の伝票は編集をロックする（現行は運用で防いでいる部分を仕組みにする。解除は管理者のみ）

### 6-5. 帳票の保存方針

- **発行した帳票は、その時点の内容を JSON で保存**（`sales_documents.snapshot`）。PDF はいつでも同じ内容で再生成できる
- **PDF ファイル本体を保存するのは「メール送付した／確定した」もの**に限る（見積書の試し出力などは保存しない）
- 請求書は確定時に PDF を保存する。インボイスの保存要件に関わるため、**保存した PDF は上書き・削除不可**
  （取消は「取消の記録」を残す）。検索は取引日・金額・取引先でできるようにする

## 8. 権限

**2026-11-14 決定: 既存タスク管理と同じ権限体系を使う。** 販売用に別の権限列は作らない。

| `users.role` | 販売管理でできること | 現行 FileMaker の対応 |
|---|---|---|
| `staff` | すべての業務（伝票・帳票・締め・マスタ） | システム管理者／マスタ管理者／承認者／標準業務ユーザ |
| `owner` | **閲覧のみ**（既存アプリと同じ扱い。`isLimitedRole`） | 閲覧ユーザ |
| `equipment_out_staff` | 販売管理は使えない（ログインしても入れない） | — |

- owner にする具体的な利用者は依頼元が追加登録する（既存の利用者管理の手順どおり）
- 判定は**必ず Worker 側**で行う（画面で隠すだけにしない）
- 現行の「承認者」「作業報告ユーザ」に当たる区別は設けない。請求の確認・承認は `staff` の誰でも押せ、**誰が押したかを記録**する。
  現場担当や協力会社に金額を見せずに作業報告だけさせたい要望が出た場合は、その時点で役割の追加を検討する（13章⑤）
- 担当者マスタの給与項目を移行しない（1章）ため、担当者詳細に機微情報は載らない
- 得意先ユーザ・仕入先ユーザは 9-2

## 9. 付加機能の提案

踏襲分の完成を優先し、**下表の「推奨」は該当フェーズに含め、それ以外は切替後に判断**する。

### 9-1. 推奨（追加費用なし）

| 提案 | 内容 | 効果 |
|---|---|---|
| 進行バー・状態バッジ | 7-1 のとおり | 伝票の現在地が一目で分かる |
| 横断検索 | 伝票番号・得意先名・件名・納品先を 1 つの検索窓から（`Ctrl+K`） | メニューをたどらずに目的の伝票へ |
| 変更履歴 | 伝票ごとに「誰が・いつ・何を変えたか」 | 金額相違の原因を追える。現行は最終変更フィールド名しか残らない |
| 締め済みロック | 締め後の伝票を誤って変えられない | 請求書と元帳の不一致を防ぐ |
| 請求締めの下書き | 確定前に結果を確認・やり直し | 締め直しの手間を減らす |
| ホームの警告と Web Push | 日程未調整・見積期限・入金遅延を通知（既存の Push 基盤） | 抜け漏れ防止 |
| メール送信履歴 | いつ・誰に・どの帳票を送ったかを伝票に記録 | 「送ったか」の確認が不要に |
| 請求書メールの一括下書き | 送付先設定のある得意先の請求書メールを Gmail 下書きへまとめて作成 | 月次の送付作業を短縮 |
| 得意先の取引履歴 | 得意先詳細に伝票と残高の推移 | 問い合わせ対応が速くなる |

### 9-2. 取引先への共有（ポータルの代替案）

現行の得意先ポータル・仕入先ポータルは、取引先ごとにアカウントを発行して運用している（計 4 件）。
新システムでは **既存の「期限つき共有リンク」（`secure_shares`）で、対象の伝票・予定表だけを閲覧できる URL を発行**する方式を提案する。

- 取引先のアカウント・パスワード管理が不要になり、社内 DB への入口を増やさない
- 閲覧記録が残る（既存 `secure_share_access_log`）
- 現行ポータルの使われ方（誰が・どの頻度で・何を見ているか）を伺ったうえで決める（13章⑥）

### 9-3. 切替後に判断（費用が発生しうるもの）

| 提案 | 内容 | 費用 |
|---|---|---|
| 入金の自動消込 | 銀行の入出金明細 CSV を取り込み、請求と突き合わせて入金伝票の候補を作る。振込手数料差額は値引伝票を提示 | 0 円（規則ベース。AI 不要） |
| 総合振込データ出力 | 支払伝票から全銀形式のファイルを出力 | 0 円 |
| 見積の下書き支援 | 件名・得意先から過去の類似見積を探し、明細の下書きを提示 | **Claude API の従量課金**（1 回あたり 1 円未満の見込み。既存の 1 日上限の対象） |
| メール文面の下書き | 状況に合わせた案内文を生成 | 同上 |
| 作業報告の要約 | 写真とメモから報告書の文面を整える | 同上（画像を送るため単価は上がる） |

AI を使う機能は、既存の安全機構（1 日の上限・停止時の通知・利用量画面）の対象に含め、**既定では無効**とする。

## 11. データ移行

### 11-1. 方式

備品・ビルメンと同じく **FileMaker から CSV を書き出し、取込スクリプト（`scripts/import-sales-*.mjs`）で Supabase へ投入**する。

- 取込は**何度でもやり直せる**ように作る（主キーは FileMaker の主キー＝UUID を引き継ぎ、同じ行は上書き）。
  開発中の検証用と、切替当日の最終取込で同じスクリプトを使う
- 文字コードは UTF-8。日付・数値・空欄の扱いは取込時に検証し、異常値は一覧にして報告する（備品移行時と同じ）
- 写真・PDF・関連書類は、FileMaker のスクリプトで**ファイル名に主キーを付けて一括書き出し** → アップロード用スクリプトで保管先へ

### 11-2. 順序

1. マスタ（会社・得意先・納品先・請求単位・仕入先・担当者・商品・区分類・消費税率・設定値）— Phase 1
2. 売上系伝票・明細、仕入系伝票・明細 — Phase 2・4（**全期間**。古い伝票も検索・複写元として使われているため）
3. 締め結果（請求管理・請求単位管理・明細）、得意先元帳、仕入先元帳 — Phase 6・7（残高の起点として必要）
4. 作業管理、出力済み帳票、関連書類、写真 — Phase 8・9
5. 切替当日: 差分ではなく**全件を取り直す**（やり直せる取込のため、手順が単純で確実）

### 11-3. 検証（突合テスト）

| 検証 | 方法 |
|---|---|
| 件数 | テーブルごとに FileMaker の件数と一致するか |
| 伝票の金額 | 全伝票について、**新システムの計算モジュールで再計算した税抜・税額・税込が、FileMaker の保存値と一致するか**を自動で照合。不一致は伝票番号つきで一覧化 |
| 請求締め | 過去の締め月（直近 6〜12 か月）を新システムで締め直し、得意先ごとの前月残高・入金・販売額・税額・請求額が FileMaker の請求管理と **1 円単位で一致するか** |
| 帳票 | 受領済みの現行 PDF 8 種と、新システムの出力を並べて目視確認（項目・金額・税率別内訳・注記） |
| 経理 CSV | 同じ月の出力を現行と比較し、列・値が完全に一致するか（差分ツールで照合） |
| 残高 | 得意先元帳・仕入先元帳の当月残高が一致するか |

不一致が出た場合は、**新システムを直す**のか**現行の値が例外（手修正など）**なのかを 1 件ずつ判定し、判定結果を本書に追記する。

### 手順2: マスタと伝票の書き出し（FileMaker Pro）

3. メニュー **「ファイル」→「レコードのエクスポート...」**
   - ファイルの種類: **「コンマ区切りテキスト（.csv）」**
   - 出力ファイルの文字セット: **「Unicode（UTF-8）」**
   - **「フィールド名を 1 行目に含める」** にチェック（選択肢がない版では「Merge（.mer）」形式を選ぶと 1 行目にフィールド名が入る）

   会社基本情報／得意先マスタ／納品先マスタ／請求単位マスタ／仕入先マスタ／担当者マスタ／商品マスタ／商品区分マスタ／消費税率／コンスタントマスタ
   - あわせて画面側ファイル **`eSales2`** の: 処理区分マスタ／曜日マスタ／サービス区分マスタ（データ側）／勘定科目マスタ／請求書種類／端数処理／課税方法マスタ／消費税区分マスタ／消費税集計方法マスタ／消費税転嫁区分マスタ
5. 伝票（売上系伝票・売上系明細・仕入系伝票・仕入系明細）は Phase 2 の前に同じ手順で

> 受け渡しは、これまでと同じくこのセッションへのアップロードで可。**得意先・金額を含むため、メール添付での送付は避ける**。

## 15. リスクと対策

| リスク | 対策 |
|---|---|
| 消費税・請求金額の不一致 | 計算の一本化（6-3）＋過去データでの自動突合（11-3）。一致を確認するまで請求書は FileMaker から出す |
| 現行仕様の読み落とし（スクリプト 490 本） | Phase 0 で計算・締め・展開の仕様を文書化。各フェーズ着手時に該当スクリプトを読む。並行運用で差を検出 |
| 無料枠の超過 | 5-3 の見通しを各フェーズ完了時に実測で更新。Storage／R2 の使用量をホームの管理者向け表示に出す |
| バックアップの失敗（100MB 上限） | Phase 1 で対策を入れ、伝票移行の前に復元まで確認（5-5） |
| 画像方式 PDF の容量・文字検索不可 | 保存対象を絞る（6-5）。請求書で問題が出る場合は、文字を埋め込む PDF 生成への切替を別途検討 |
| 並行運用中の二重入力の負担 | フェーズごとに「この業務は新システムを正とする」範囲を明示。最終切替まではデータを FileMaker から取り直せる作りにする |
| 画面数増による既存機能への影響 | 販売セクションの遅延読み込み・コードの分離（5-1） |
| 月次処理の検証に時間がかかる | Phase 6 を切替時期から逆算して前倒し（10章） |

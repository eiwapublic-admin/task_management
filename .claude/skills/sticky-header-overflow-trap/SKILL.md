# 横スクロール（overflow-x: auto）と position: sticky の相性問題

カンバンボードの列見出しをスマートフォン幅で固定表示にする実装（一覧・カンバンの
狭幅横スクロール + 列ごとの sticky ヘッダー）で、3回連続で見た目が崩れ、その都度
原因が異なる罠だった。**すべて根っこは同じ1つのCSS仕様**に行き着く。新しく
sticky ヘッダーを書く前、あるいは「固定表示のはずなのに位置がおかしい」を
調査する前に、必ずこの文書を読むこと。同じ罠を3回踏み直す必要はない。

## いちばん大事な結論（先に読む）

**`overflow-x: auto` を持つ要素は、`overflow-y` も自動的に `auto` になる。**
CSS Overflow の仕様で、`overflow-x` と `overflow-y` の片方が `visible` で
もう片方がそうでない場合、`visible` の方が `auto` に矯正される。これは
**`overflow-y: visible` を明示的に書いても上書きできない**（仕様上の強制なので、
詳細度をいくら上げても効かない）。

横スクロールが欲しくて `overflow-x: auto` を書いた要素は、頼んでもいないのに
「意図しない縦のスクロールコンテナ」になる。そして `position: sticky` の
固定位置は「**最も近い祖先のスクロールコンテナ**」を基準に計算される。
本来ページを基準に固定したかった見出しが、この横スクロール用の要素を基準に
固定されてしまい、位置が大きくずれる——これが今回3回のうち最初の不具合の正体。

対処は2択。**どちらを選ぶかは、sticky にしたい要素が横スクロールする範囲の
外にあるか、中にあるかで決まる。**

| 状況 | 対処 |
|---|---|
| sticky にしたい要素が、横スクロールする範囲の**外**にある（例: 表の外側のタイトル・絞り込みバー） | 横スクロールの対象を**専用の狭いラッパー**に閉じ込め、sticky要素はその外に出す |
| sticky にしたい要素が、横スクロールする範囲の**中**にある（例: 横スワイプで切り替わる列そのものの見出し） | ページ基準で固定するのを諦め、**その要素自身を高さ制限つきの縦スクロールコンテナにする**。sticky はページではなくその要素基準で効かせる |

## 症状 → 原因 → 対処（マトリクス）

| 症状 | 原因 | 対処 |
|---|---|---|
| 横スクロールを追加したら、外側にあったはずの sticky なタイトル・絞り込みバーの位置までおかしくなった | 横スクロール用の `overflow-x: auto` を、タイトル・絞り込みバーも含む広い親要素に付けてしまい、それらも巻き込んで意図しないスクロールコンテナになった | 横スクロールの対象を**表そのものだけを包む専用ラッパー**に絞り込む（`.logs-table-wrap` 参照）。外側の要素からは `overflow-x` を外す |
| 横スワイプで切り替わる列（カンバン等）の見出しが、列の下の方や画面の外にずれて表示される | 列を横スクロールさせる `overflow-x: auto` が、同じ要素の `overflow-y` も `auto` にし、列見出しの sticky 基準がページからその列自身にすり替わった | ページ基準の固定を諦め、**列自身を `height` 上限つきの縦スクロールコンテナにする**。見出しは `top: 0` でその列の中で固定表示する（下記「対策B」） |
| `height` を calc で計算しても、何度式を直しても表示が変わらない | 同じ要素（または共通の基底クラス）に `min-height` が設定されていて、`height` より大きいため `min-height` が勝っている（CSS の仕様。競合したら `min-height` が常に優先） | 対象の要素の**computed style で `min-height` を確認する**。式をいじる前にここを疑う。競合する幅では `min-height: 0` で明示的に解除する |
| スクロールすると、見出しの少し上に隙間があり、そこにスクロール中のカードや行の内容が透けて見える | 見出しが `top: 0` で貼り付いている先のスクロールコンテナ自身に `padding-top` が付いている。padding は「予約された空きスペース」であって、そこに何かを不透明に塗って蓋をしているわけではない。スクロールで子要素の端がその padding 帯にちょうど重なると、そのまま透けて見える | その `padding-top` を**コンテナ自身からは外し、sticky な見出し自身の内側の余白に付け替える**。見出しは不透明な背景を持つので、その帯もまるごと覆われる |

## 対策A: 横スクロールの対象をラッパーに閉じ込める

sticky にしたい要素（例: 画面タイトルや絞り込みフォーム）が、横スクロールが
必要な要素（例: 幅の広い表）の**外側**にあるなら、これが素直な対処。

```jsx
{/* タイトル・絞り込みはここ。overflow-x は付けない → sticky が正しくページ基準になる */}
<div className="ui-sticky-head">…</div>

{/* 表だけを専用ラッパーで包み、横スクロールはここに閉じ込める */}
<div className="logs-table-wrap">
  <table>…</table>
</div>
```

```css
/* 表の外側の要素には overflow-x を書かない。表を包むラッパーだけに付ける */
.logs-table-wrap {
  overflow-x: auto;
  -webkit-overflow-scrolling: touch;
}
```

以前は「表を含むセクション全体」に `overflow-x: auto` を付けていたため、
セクション内のタイトル・絞り込みバーの sticky まで巻き込んで壊れていた。
ラッパーを表だけに絞ったことで、外側の sticky 要素は無関係のまま正しく動く。

**ただし、ラッパーの中にも sticky 要素（例: 表の列見出し `<th>`）を置く場合は、
そこは対策Aの範囲外**——同じ罠がラッパー自身との間で再発する。その場合は
その幅では列見出しの固定表示自体を諦めて `position: static` に戻すか、
下記の対策Bを適用する。

## 対策B: その要素自身を独立した縦スクロールコンテナにする

sticky にしたい要素が、横スクロールする範囲の**中**にある場合（カンバンの
各列のように、横スワイプで切り替わる要素そのものの見出しを固定したい場合）は、
「ページ基準で固定する」という前提自体を捨てる。**そのブロックを、ページとは
独立した縦スクロールコンテナに仕立て、見出しはその中で `top: 0` に固定する。**

```css
@media (max-width: 768px) {
  /* 横スワイプで切り替わる列を包む要素。ここに overflow-x が付いていることで、
     中の各列も CSSの仕様上「意図せず」縦のスクロールコンテナになりうる */
  .kanban-columns {
    display: flex;
    overflow-x: auto;
    scroll-snap-type: x mandatory;
  }

  .kanban-column {
    flex: 0 0 82%;
    /* 既定の min-height（カードが少ない列を寂しく見せない用途）が
       この height を下から突き上げて無効化するため明示的に解除する */
    min-height: 0;
    /* 列の開始位置（AppHeaderの実測高さ・その下のツールバーの実測高さ・
       余白）を実測CSS変数から逆算し、画面の残り高さぶんだけ確保する。
       これで列自身が「意図して」独立した縦スクロールコンテナになる */
    height: calc(
      100dvh - var(--app-header-h) - var(--sticky2-h, 0px) - var(--space-4) -
        env(safe-area-inset-bottom) - var(--space-3) * 3 - var(--space-2)
    );
    overflow-y: auto;
    -webkit-overflow-scrolling: touch;
    /* 上端の余白は列自身ではなく見出し側に持たせる（次の理由） */
    padding-top: 0;
  }

  .kanban-column-header {
    position: sticky;
    top: 0; /* ページ基準ではなく、この列自身のスクロール基準で固定する */
    /* 列から外した分の余白をここで持つ。見出しの不透明な背景がこの帯も覆う */
    padding-top: calc(var(--space-1) + var(--space-3));
    background: inherit; /* 下を通過するカードが透けないよう、列と同じ背景を継ぐ */
  }
}
```

ポイントは3つ。

1. **`overflow-x` が引き起こす `overflow-y: auto` の強制を、バグとして避けるのではなく、そのまま設計として使う。** 「意図せずスクロールコンテナになる」なら、逆に「意図して」その大きさ・スクロール方向を決めてやればよい。
2. **高さは実測値から逆算する。** `AppHeader` の実際の高さ（折り返しやノッチ対応で可変）を `ResizeObserver` で測って CSS変数に反映するヘルパー（このリポジトリでは `src/lib/useStickyHeightVar.js`）を使い、`--app-header-h` のような変数から `calc()` で「画面の残り高さ」を出す。固定値を決め打ちしない。
3. **同じ要素・共通の基底クラスに `min-height` が無いか確認する。** カードが少ない列を寂しく見せないための `min-height: 400px` のような既存ルールが、上記の `height` を静かに無効化することがある（`height` と `min-height` が競合すると `min-height` が勝つのはCSSの基本だが、意識していないと何を直しても変化しない現象として現れる）。狭幅では `min-height: 0` で明示的に解除する。

## padding は不透明な蓋ではない

対策Bで見出しを `top: 0` に固定しても、**コンテナ自身に `padding-top` が
残っていると別の不具合が出る**。padding は単なる「予約された空きスペース」で、
そこに何かを塗って隠しているわけではない。子要素がスクロールでその帯を
通過すると、下記の順でそのまま見えてしまう。

- 見出し（`position: sticky`）は自分の**own box**しか覆わない。コンテナの
  `padding-top` はコンテナ自身の領域であり、見出しの外側にある。
- コンテナの背景色は通常そこに塗られているが、子要素（カード等）は
  スタッキング上、コンテナの背景より**上**に描画される。子要素の端が
  ちょうどその padding 帯と重なる高さまでスクロールされると、コンテナの
  背景ではなく子要素がそこに見える。

対処は、その `padding-top` をコンテナからは外し、**見出し自身の
内側の余白**に付け替えること。見出しは不透明な背景を持つ（対策Bの
`background: inherit` 参照）ので、この帯もまるごと見出しの中に取り込まれ、
覆われる。

## デバッグ技法: `getBoundingClientRect()` は見た目のクリップを教えてくれない

この種の不具合を調査していると「カードが列の外（クリップされているはずの
領域）にまで描画されている」ように見える瞬間がある。`getBoundingClientRect()`
で座標を取ると、一見その予想を裏付けるような値が返ることがあるが、
**これは罠**。`getBoundingClientRect()` は要素の**レイアウト上の座標**を
返すだけで、祖先の `overflow` によって実際に見えているかどうかとは無関係。
スクロールで動いた要素は、クリップされていても座標上は普通に外へ出ていく。

「その座標に実際に何が描画されているか」を確かめたいときは、
**`document.elementFromPoint(x, y)`** を使う。これはブラウザが実際に
ペイントした結果に対するヒットテストなので、視覚的な真実を返す。

さらに、不具合が特定のスクロール量でだけ起きる（＝子要素の端がちょうど
問題の帯と重なる瞬間だけ）場合は、静止画のスクリーンショットを1枚撮って
目視するよりも、**スクロール位置を細かく刻んで機械的に走査する方が確実**。

```js
// scrollTop を 0〜400px まで 10px 刻みで動かしながら、
// 問題の帯（列の上端付近の座標）に何が描画されているかを確認する
for (let st = 0; st <= 400; st += 10) {
  const info = await col.evaluate((el, scrollTo) => {
    el.scrollTop = scrollTo
    const r = el.getBoundingClientRect()
    const x = Math.round(r.left + r.width / 2)
    const y = Math.round(r.top) + 6 // 疑わしい帯のy座標
    const hit = document.elementFromPoint(x, y)
    return hit ? hit.className : null
  }, st)
  console.log(`scrollTop=${st} -> ${info}`)
}
```

修正前はこの走査でスクロール量に応じて `task-card` 系のクラスが混ざって
検出され（＝カードが透けて見える瞬間がある）、修正後はどのスクロール量でも
見出しのクラスだけが検出される（＝透けて見える瞬間が無い）ことを、
目視ではなく数値で確認できる。

## 検証の型（Playwright + ローカルの Vite dev server）

- `playwright-core` とローカルにバンドルされた Chromium で、`vite` の
  dev server（例: `npx vite --port 5199`）に対してヘッドレスで検証する。
  API 応答は `page.route('**/api/**', ...)` でモックし、バックエンドを
  立ち上げずに画面だけを再現する。
- 確認すべき指標は最低限これだけ:
  - `document.documentElement.scrollWidth > clientWidth`（横スクロールが
    意図せず出ていないか）
  - `document.documentElement.scrollHeight` と `window.innerHeight` が
    一致するか（対策Bで、ページ側に余計な縦スクロールが残っていないか）
  - 対象要素の `scrollTop` を動かしても `window.scrollY` が動かないこと
    （縦スクロールが意図通り「列の中」に閉じ込められているか）
  - 上記の `elementFromPoint` によるスクロール量スイープ
- **これは Chromium 経由の検証であり、実機の Safari/WebKit 特有の挙動までは
  保証しない。** iOS の実機で position: sticky の挙動が違う可能性は残るため、
  実機確認の依頼を都度添えること（プロジェクトスキル
  `multi-env-attachment-preview` にある通り、WebKit固有の描画差はChromiumでは
  そもそも再現しない）。
